# review-plan（plan のレビュー）

plan をレビューする。plan は spec（何を・なぜ）と実装のあいだに置く技術設計の文書で、読み手は主に実装するエージェント。人間が全文を読むとは限らない。

だからこのレビューの仕事は2つ。

- **事実の指摘**: 節が欠けている、spec やコードベースと食い違っている。正誤が言えるもの
- **人間が決める問い**: plan が決めておらず、実装者が推測するしかない決定。選択肢を添えて返し、人間はこの一覧に答えるだけで済むようにする

指摘は、正誤の基準（spec・コードベース・プロジェクトの規約）に照らせるものに限る。基準の無い指摘は、レビュアーの好みに収束する。

## 入力

- **plan**: ファイルのパス、または PR（plan のファイルを含むもの）
- **spec**（あれば）: チケット・issue・PRD の本文。plan からリンクされていれば自分で取りに行く
- **コードベース**: plan が対象にするリポジトリ

plan と実装が同じ PR に入っているなら、コードベースは**ベースブランチの状態**で読む。実装済みのコードを読むと、plan が決めていないことまでコードから答えが見えてしまい、推測の洗い出しが効かなくなる。ベースブランチの worktree を作り、作業が終わったら消す。

## 1. 基準を集める

- **プロジェクトの plan 規約**: `CLAUDE.md` / `AGENTS.md`、`.claude/skills/` の中の plan・design doc・spec 用のスキル、`docs/README.md` や `docs/plans/` の README。規約が必須と定めた節は、規約に従う。規約が必須を定めていない（「省略してよい」の参考テンプレートしか無い）なら、下の必須6節で見る
- **spec**: 要件と受け入れ条件を一覧にする
- **プロジェクトの不変条件・規約のドキュメント**（あれば）

規約が無いときの必須6節:

1. Context（why と spec へのリンク）
2. Goals / Non-goals
3. Design（データ、API の契約、振る舞い、副作用、既存とのつながり）
4. Decisions（選んだもの / 選ばなかったもの / 理由）
5. Risks and rollout（認証・認可、移行と後方互換、ロールアウトと切り戻し、観測）
6. Verification and open questions

**完了条件**: 照らし合わせる基準（必須の節、spec の要件一覧、プロジェクトの規約）が手元にそろっている。spec が見つからなければ、無いことを記録して先へ進む。

## 2. 推測の洗い出しを撒く

実装担当のサブエージェント（general-purpose）を**3体、1メッセージで並列に**立てる。渡すのは plan とコードベースのパスと下の依頼文だけにする。先入観なく読ませるため。

> この plan を、このコードベースに実装する。ただしコードは書かない。実装者として下す決定を列挙する。
>
> 対象は外から見える決定に限る: データ（テーブル・カラム・型・制約・既定値）、API（ルート・リクエストとレスポンスの形・ステータスとエラー・権限）、各エッジケースと境界値での振る舞い、副作用（書き込み・ジョブ・通知・外部呼び出し・ログ）、移行・ロールアウト・後方互換。関数の分け方・ファイル構成・命名は対象外。
>
> 各決定に、1文の具体的な内容と根拠を付ける。根拠は3つのどれか:
> - PLAN: plan のどこに書いてあるか（数語を引用）
> - CODE: どのファイルがそう決めているか
> - GUESS: 自分で選ぶしかなかった。あり得た別の選択肢を1つ書く
>
> plan が触れておらず、コードも決めていないなら GUESS にする。既存の handler を真似て決めたなら、それは CODE。15〜40件を目安にする。

3体立てるのは取りこぼしを減らすため。1体だけが拾う重要な GUESS がある。逆に、3体が同じ答えを出しても、それが GUESS なら plan が決めたことにはならない。同じモデルは、plan が黙っている箇所で同じ既定値（フラグは無し、監査は残さない、状態に関係なく操作できる）を選びやすい。

**完了条件**: 3体の結果がそろっている。

## 3. 事実を照らし合わせる

サブエージェントの結果を待つあいだに、自分で次を確かめる。

- **節の欠け**: 必須の節がそろっているか。「なし」と書いてあれば合格にする。Open questions の外に TODO・TBD などの未決が残っていないか
- **spec との対応**: spec の要件・受け入れ条件がそれぞれ Goals か Non-goals に入っているか。受け入れ条件ごとに Verification に確かめ方があるか。spec に無いものを Goals が足していないか
- **コードベースとの対応**: plan が挙げたファイル・型・テーブル・エンドポイントが実在するか（新規と書いてあるものは、まだ無いか）。plan の記述が既存の規約や実装と食い違っていないか（権限、エラーの返し方、ページング、既存のカラムの意味）
- **プロジェクトの規約との対応**: 不変条件・規約のドキュメントに反する決定が無いか

指摘にするのは、食い違いの両側を引用で示せたものだけ。plan の記述と、spec・コード・規約の該当箇所。

**完了条件**: 4つの観点すべてについて、指摘か「問題なし」が出ている。

## 4. 問いにまとめる

3体の GUESS を集め、同じ決定を指すものを1件にまとめる。次のものは落とす。

- 手順3の事実の指摘で既に拾ったもの
- 外から見えない決定（内部構造の選び方）
- どちらを選んでも振る舞いが変わらないもの

残ったものを、外れたときの影響で振り分ける。

- **問いにする**: データを失う・壊す、権限やセキュリティ、ユーザーに見える振る舞いが変わる（デプロイの瞬間に変わるものも含む）。この順に並べ、**上位10件**までにする
- **件数だけ書く**: ログ・監査の粒度や画面の注記など、外れても上の3つに響かないもの。10件に収まらなかった問いも、ここに件数で足す

件数の多さそのものが「plan が決めきれていない」という所見になる。

各問いは、plan を開かなくても答えられる形にする。

- 何を決める必要があるか（1文）
- 選択肢（実装担当が選んだもの、あり得た別のもの）
- 既存のコードが一方を示唆しているなら、その根拠

**完了条件**: 問いが10件以内に絞られ、それぞれに選択肢がそろっている。

## 5. 返す

次の形で返す。plan の修正は、結果を受け取った側が行う。

```markdown
## 事実の指摘
- [節の欠け / spec / コード / 規約] 指摘の1文
  - plan: 「引用」
  - 基準: 「引用」（ファイルパス・spec の該当箇所）

## 人間が決める問い（N 件中 上位 M 件）
1. 決めること
   - 選択肢: A（実装担当の多くが選んだ） / B
   - 示唆: 既存の X は A に揃っている（ファイルパス）

ほかに、影響の小さい推測が N 件（ログ・監査・注記など）

## 推測の割合
外から見える決定のうち GUESS が占めた割合（3体それぞれ）
```

推測の割合は、plan の決めきり具合の目安として付ける。
