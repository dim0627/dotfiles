現在開いているリポジトリの Sentry issue をトリアージする。成果物は Sentry の UI が出せないもの — **コードベースと突き合わせた対応要否の判断**。

## 前提

- Sentry MCP が認証済み（未認証なら `/mcp` で認証してもらう）
- 現在ディレクトリが Git リポジトリ

## 引数

- **引数なし**: 対象プロジェクトの未解決 issue を束ねて分類（コードは読まない、安い）
- **`--deep`**: 🔴🟡 に分類されたクラスタについてコードを読み、原因仮説と修正方針まで出す（高い）
- **`--deep <ISSUE-ID>`**: 特定 issue だけ深掘り
- **`--period <24h|7d|14d|30d|90d>`**: 集計期間（既定 `30d`）
- **`--env <名前>`**: 対象環境を明示（既定は手順 2 で自動判定）
- **`--ask`**: 判定軸の較正結果を自動で採用せず、`AskUserQuestion` で確認してから判定する

## 手順

### 1. 対象 Sentry プロジェクトの解決

**リポジトリ名と Sentry プロジェクト名は別物として扱う。** monorepo なら 1 リポジトリが web / api など複数の Sentry プロジェクトに跨るのが普通で、命名規則もプロジェクトごとにバラバラ（区切り文字の有無、`api-` 前置と後置の混在など）。**複数プロジェクトを許容し、実測した一覧の中から選ぶ。**

以下の順で解決し、確定した時点で打ち切る。

**1-a. リポジトリ内の Sentry ビルドプラグイン設定から抽出（最も確実）**

```bash
grep -rnE --exclude-dir=node_modules --exclude-dir=.git --exclude-dir=dist --exclude-dir=.next --exclude-dir=worktrees '(org|project)[[:space:]]*:[[:space:]]*["'"'"']' . | grep -iE 'sentry|org:|project:'
```

`@sentry/*` の vite / next / webpack プラグイン設定（`vite.config.ts`, `next.config.js` 等）に `org` と `project` が平文で入っている。**`.claude/worktrees/` 配下や `dist/` のコピーは必ず除外する**（古い値を拾うため）。

**1-b. 見つからない・数が足りない場合**

`SENTRY_DSN` があるかを確認する:

```bash
grep -rnE --exclude-dir=node_modules --exclude-dir=.git 'SENTRY_DSN' . | head
```

DSN 末尾の数値はプロジェクト ID だが、`find_projects` はスラッグしか返さないため DSN からプロジェクト名は逆引きできない。**DSN の存在は「このアプリも Sentry に送っている」という根拠としてのみ使う**（＝プロジェクトを 1 つ見落としているサイン）。

`find_organizations()` → `find_projects(organizationSlug)` でスラッグ一覧を取り、リポジトリ名とファジーに突き合わせる。リポジトリ名は次で取る:

```bash
git remote get-url origin
```

突き合わせ対象は「リポジトリ名」「アプリ名（monorepo なら `apps/*` のディレクトリ名）」の両方。ドット・ハイフン・アンダースコアを除去した上での部分一致で見る。

**1-c. 候補が複数あって絞れない場合**

`AskUserQuestion` で対象プロジェクトを選んでもらう。見落としたプロジェクトの障害が「異常なし」として報告されるのが最悪のケースなので、迷ったら聞く方に倒す。

**完了条件**: 対象プロジェクトが確定し、1-b で DSN が見つかったアプリがすべて対象に含まれていること。

### 2. 本番環境の名前を特定する

**`environment:production` を決め打ちしてはいけない。** ホスティング環境やデプロイ設定によって値が変わる。実測で確認された例:

- `production`（標準）
- `vercel-production` / `vercel-preview`（Vercel の Sentry 連携が自動で付ける）
- `prd` / `prod` / `stg`（プロジェクト独自の命名）

決め打ちすると、**エラーが出ているプロジェクトを「異常なし」と報告する**（クエリが 0 件を返すため）。これはこのスキルの最悪の壊れ方。

`--env` が指定されていればこの手順はスキップする。指定がなければ以下の順で決める。

**2-a. 実測して候補を出す（これが正）**

手順 1 で解決した各プロジェクトについて実行する。

```
search_events(
  organizationSlug=<org>,
  projectSlug=<project>,
  dataset='errors',
  fields=['environment', 'count()'],
  sort='-count()',
  period=<引数の期間 / 既定 30d>,
  limit=20
)
```

Sentry に実際に届いている値だけが候補になる。プロジェクト単位に絞ることで、プロジェクト数の多い org でも件数上限に当たらない。

**2-b. コードベースで候補を絞る**

2-a の候補が複数あって本番相当が一意に決まらない場合、リポジトリ側の設定を根拠に選ぶ。Sentry SDK 初期化時の `environment` 指定、デプロイ設定、CI ワークフローの環境変数などが手掛かりになる。

**コードベースは 2-a の実値の中から選ぶための手掛かりとして使う。** デプロイ設定上の環境名と Sentry に届く `environment` タグの値が食い違う実例がある（CI が `prd` / `stg` を渡していたが、Sentry 側の実値は `production` だった。SDK 側で別の値にマップされていたため）。

**2-c. それでも決まらない場合**

`AskUserQuestion` で 2-a の実値を選択肢として提示し、選んでもらう。

**完了条件**: 採用した環境名が 2-a の実値に存在すること。

### 3. issue の取得

解決した各プロジェクトについて実行する。

```
search_issues(
  organizationSlug=<org>,
  projectSlugOrId=<project>,
  query='is:unresolved environment:<手順2で特定した値>',
  period=<引数の期間 / 既定 30d>,
  sort='freq',
  limit=100
)
```

- `sort='freq'` にする。発生数順が実害に一番近い
- 0 件だった場合、**手順 2 の環境名が間違っている可能性をまず疑う**。`environment` フィルタを外して再取得し、本当に 0 件かを確認してから「異常なし」と報告する

### 4. 根本原因ごとのクラスタリング（このスキルの核）

**Sentry は culprit（エンドポイント / トランザクション）単位でグルーピングするため、1 つの根本原因が何個もの issue に分裂する。** 実例として、DB 接続エラー 1 件が `POST /events` `POST /chat` `GET /me/usage` … と 10 個以上の別 issue になっていたことがある。件数を数える前に必ず束ね直す。

以下が一致するものは同一クラスタの候補として扱う:

- エラー型が同じ（`Failed query: ...`、`TimeoutError`、DB ドライバの例外型 等）
- エラーメッセージの可変部（SQL の列名・パラメータ・URL のID）を除いた骨格が同じ
- first seen の時間帯が近い（同じデプロイ / 同じ障害ウィンドウ）

**判断に迷ったら代表 issue を 1 件だけ `get_sentry_resource` で開いて真因を確認する。** 表層のメッセージ（`Failed query: select ...` のような、発行したクエリがそのまま出るもの）と真因は別物なことが多い。真因は `During handling of the above exception, another exception occurred` の下に chain されて出る（DB ドライバが返した HTTP 5xx など）。ここまで見ないと束ねられない。

**issue category が違うものは別の群として扱う。** `search_issues` の結果には `Category` が付くことがある（`error` / `db_query` 等）。パフォーマンス系（`Slow DB Query` など）はエラーとは実害の意味が違う（判定は手順 6 参照）。

束ねたら、クラスタ単位で「合計イベント数 / 影響ユーザー数 / 最終発生 / first seen / 含まれる issue 数 / category」を集計する。

**完了条件**: 手順 3 で取得した**全 issue がいずれかのクラスタに属していること**。束ねられなかったものは 1 件単独のクラスタとして残し、ロングテールも数に含める。

### 5. 判定軸の較正

**閾値は毎回データの分布から決める。** 「何件で重大か」はプロダクトの規模・トラフィック・計測設定に完全に依存するので、固定値を書くとどこかのプロジェクトで必ず壊れる。**軸のセットは固定し、どの軸が識別力を持つかを取得したデータの分布から毎回決める。**

| 軸 | 使えるかの判定 | 使えない場合 |
|---|---|---|
| 影響ユーザー数 | 全クラスタの userCount の最大値が 2 以上で、かつ値にばらつきがある | **軸ごと無効化**し、イベント数に重みを寄せる |
| イベント数 | 常に有効。ただし絶対数でなく全クラスタ中の相対位置で見る | — |
| 継続性（最終発生の新しさ）| 常に有効。規模に依存しない普遍軸 | — |
| 継続期間（first seen 〜 最終発生）| 常に有効 | — |
| 新規 / 再発（regression・escalating）| substatus が取得できる場合 | 無効化 |
| リリース相関 | `git log` でデプロイ相当のコミットが特定できる場合 | 無効化 |

**ユーザー数の軸は高確率で無効になる。** 個人プロダクトと B2B 業務システムの両方で userCount が 0〜1 に張り付いていた実測がある（ユーザーコンテキスト未設定、または少人数利用）。有効性を確認せずに主軸に据えると全クラスタが同点になって判定が機能しなくなる。逆に、消費者向けで実際にばらついているなら最も実害に近い軸なので、**使える時は最優先の軸にする**。

「多い / 少ない」は取得した全クラスタの分布の中での相対位置（最大クラスタとの比、中央値との比）で判断する。

較正の結果は**報告の冒頭に 1 行で明示する**。自動判定が外れていてもユーザーが即座に訂正できるようにするため。

```
較正: 対象 <org>/<project> ・環境 <env> ・期間 30d ・有効な軸 = イベント数(相対) / 継続性 / リリース相関 ・無効 = ユーザー数(全件 0〜1 のため)
```

`--ask` が指定された場合は、この較正結果を自動採用せず `AskUserQuestion` で軸の確認を取ってから判定に進む。

### 6. 判定

較正した軸を使い、相対評価で分類する。

| 条件 | 判定 |
|------|------|
| 有効な軸で影響が上位 かつ 最終発生が直近（24h 以内）| 🔴 即対応 |
| 最終発生が直近 かつ first seen から途切れず継続 | 🔴 即対応 |
| 直近リリース以降に first seen（デプロイ起因の疑い）| 🔴 即対応 |
| 一度 resolve されたのに再発（regression / escalating）| 🔴 即対応 |
| 最終発生が直近だが影響が下位（散発）| 🟡 要調査 |
| 最終発生が期間の大半より前（既に収束）| 🟡 要調査（優先度低）|
| 下のノイズ判定に該当 | ⚪️ ノイズ |

パフォーマンス系（`db_query` 等）は別基準で判定する。**継続的に発生していて、かつ対象が同一エンドポイントに集中しているものだけ 🟡 に上げる**。単発の閾値超過は 🟡（優先度低）で十分。

直近リリースとの相関を見るときは `git log --oneline -20 --since='<期間>'` でデプロイ相当のコミットと first seen を突き合わせる。

**完了条件**: 手順 4 の**全クラスタに 🔴 / 🟡 / ⚪️ のいずれかが付いていること**。

#### ノイズ判定

**該当したら必ず「なぜノイズと判断したか」を書く**（後で誤判定を検証できるように）。プラットフォームによらず、以下の 3 原理で分類する。

**原理 1: 自コードの制御外で発生している**

自分が書いていないコードが起点になっているもの。スタックや識別子が自コードに存在しないかで判定する。

- 例（Web）: `Can't find variable: WKWebView_RemoveAllHighlights`、`window.onorientationchange is not a function` — SNSアプリ内ブラウザの注入スクリプト由来
- 例（Web）: スタックに `chrome-extension://` / `moz-extension://` — ブラウザ拡張由来
- 例（Web）: `Error: Aa`、`Error: fa` のように型名が 1〜2 文字 — サードパーティスクリプトのミニファイされた例外

**原理 2: ユーザー操作の正常な帰結**

- 例: `AbortError: The operation was aborted.` — 画面離脱・リロード。数が少なければ無視可

**原理 3: 想定内の業務例外が過剰に送信されている**

アプリが自分で投げている想定内の例外が、そのまま Sentry に送られているもの。**自然文（多くは日本語）のエラーメッセージ・アプリ独自の例外型・大量発生・ユーザー影響が見えない、の組み合わせが目印**。「権限がありません」「対象のデータが見つかりません」のような、本来 4xx で返して終わる類のもの。

**これは「ノイズ」だがバグではなく計装の問題**なので、扱いを分ける。ignore で消すのではなく、**Sentry に送信しないようフィルタする（4xx 相当は捕捉対象から外す）ことを提案する**。報告では ⚪️ に置きつつ「計装の見直し」として明示する。件数が多いとノイズに埋もれて本物のエラーが見えなくなるので、多いなら計装の見直しを提案に含める。

#### ノイズと実害が分かれるもの

**`Load failed` / `Network error` / タイムアウト系はホストが自分の管理下かで意味が変わる。**

- 外部ホスト・散発 → ユーザー側のネットワーク断。⚪️ ノイズ
- **自ドメイン（外部SaaSを自ドメインの CNAME で配信しているケースを含む）・継続中** → CNAME / 証明書 / CDN 設定の障害。🟡 以上に上げる

### 7. 深掘り（`--deep` 指定時のみ）

`references/deep-dive.md` を読んで実施する。`--deep` の指定がなければこの手順は飛ばす。

### 8. 報告

クラスタ単位で、優先度順に報告する。冒頭に手順 5 の較正結果を必ず置く。

```
較正: <org>/<project> ・環境 <env> ・期間 30d
      有効な軸 = イベント数(相対) / 継続性 / リリース相関 ／ 無効 = ユーザー数(全件0〜1のため)
```

### 9. ステータス変更（承認が必要）

**`update_issue` による resolve / ignore / assign は、判定を報告してユーザーの明示的な承認を得てから実行する。自動では絶対に実行しない。**

誤って ignore すると、その問題は二度と通知されず「静かに消える」。依存更新PRの自動マージと違い、CI もロールバックも誤りを拾ってくれない。判定と根拠の提示までがこのスキルの責務。

承認を得たら `references/status-change.md` を読んで実行する。
