# review-code（盲検レビュー）

変更を**盲検**でレビューする。書いた本人の意図を知らない読み手として、**書いてあることだけ**から判断する。

狙うのは、静的チェックが緑になった後に残る欠陥 — **落ちない・型も通る・lint も通る、それでも静かに間違っている**もの。lint と型検査が拾えるものはそちらに任せ、ここでは探さない。

このスキルは1回のレビューで完結する。反復は呼び出し元の仕事なので、周回や停止条件はここでは扱わない。

## 入力

呼び出し元から受け取るのは次のものだけ。

- **対象** — ファイルの一覧、または差分の取り方（`git diff <fixed-point>...HEAD` など）。渡されなければ `git diff @{upstream}...HEAD` と `git diff HEAD` の両方を既定にする。コミット済みと作業ツリーの両方を拾うため。upstream が無ければ `git diff main...HEAD` に落とす。どれも空なら、何をレビューするのかを聞く
- **除外** — レビュー対象外のパス（`docs/` など）。**テストファイルも既定で対象に入れる。** 書いた本人が同じ思い込みでアサートしていれば、テストは通ったまま間違っている。アサートの向き、setup / teardown の非対称、消えたケースは、このスキルが狙う欠陥そのもの
- **仕様**（あれば） — issue / PRD の本文。取得済みのテキストで受け取る
- **追加観点**（あれば） — 今回とくに見てほしい点
- **判定済み台帳**（あれば） — 既に却下された指摘。同じものを再提示しない

判断の材料は、この入力とリポジトリから自分で読んだコードに限る。**実装の経緯や意図の説明を持っている場合も、レビューには使わない。** それを混ぜた時点で、書いた本人と同じ盲点を引き継ぐことになる。盲検が崩れるとこのスキルの値打ちは丸ごと消える。

## 手順

### 1. 対象を確定し、レンズの本数を決める

差分の取り方を渡されたなら実行して、対象ファイルの一覧を出す。除外を適用する。

参照が解決しない、差分が空、といった失敗はここで止める。レンズを撒いた後に発覚させない。

`git diff --shortstat` で差分の行数とファイル数を数え、本数を決める。

- **200 行未満、かつ変更ファイル 6 未満** — A群を1本ずつ、B群は**まとめて1本**に渡す（6〜7本）
- **それ以上** — A群・B群とも1本ずつ（10〜11本）

小さい差分で B群を束ねるのは、読む量が少なければ1人で全部の観点を視野に入れられるから。

**完了条件**: レビュー対象のファイルと、立てるレンズの本数が決まっている。

### 2. レンズを並列に当てる

各レンズについて `blind-reviewer` サブエージェントを1つ立て、**1メッセージにまとめて**投げる。各エージェントには対象・除外・仕様・追加観点・台帳と、そのレンズの担当範囲を渡す。

レンズを分けるのは、1人に全部見せると見落としが1人分の偏りに揃うから。担当を分けた方が網が広がる。

各レンズには変更ファイルを**全部**渡す。行数の少ないファイル（フック・薄いラッパ・設定）は流し読みされやすいが、同じ差分の中の兄弟ファイルと食い違っている、共通ヘルパを迂回している、といった指摘はそこに出る。

1レンズが返す候補は最大6件（B群をまとめて渡した1本は10件）。それより多く見つけたら、失敗シナリオが具体的なものから選ばせる。**失敗シナリオを1文で言えるものは、確信が持てなくても候補に入れさせる。** 落とすかどうかは次段の採点者の仕事で、ここで消えたものは採点にすらかからない。

#### A群

- **行ごとの走査** — 差分の各ハンクを1行ずつ読み、続けてハンクを含む関数の全体を読む。**触った関数の中なら、変更されていない行のバグも対象**。差分がその経路を再び通るようにした以上、今回の変更の一部として扱う。各行について「どんな入力・状態・タイミング・プラットフォームなら、この行は誤りになるか」を問う。反転した条件、off-by-one、null / undefined 参照、`await` 漏れ、falsy な 0、変数の取り違え、catch での握り潰し、正規表現のメタ文字エスケープ漏れ。
- **消えたものの追跡** — 差分が削除・置換した行それぞれについて、それが守っていた不変条件や挙動を名指しし、新しいコードのどこで再確立されているかを探す。見つからなければ候補。外れたガード、落ちたエラー経路、緩められた検証、消えたテストが覆っていたケース。
- **波及** — 変更した関数・型・シグネチャを Grep して呼び出し元を全部当たり、壊れる呼び出しを探す。新しい事前条件、戻り値の形の変更、新しい例外、順序やタイミングへの依存。呼び出し先にも同じことを問う。
- **名乗りと実体** — 各出力（値・イベント・戻り値・フィールド・状態）について、名前・型・コメントが宣言している意味を導き、実行経路を追って実際にその意味の値になるかを確かめる。定数しか返さないフィールド、意図しない経路で発火するイベント、名乗りと実挙動がズレた戻り値。ここで出るのは命名の問題ではなく挙動の問題で、名前は照合の物差しにすぎない。
  - **現在の状態だけでなく、この変更が意図している終了状態からも推論する。** 差分やリポジトリ内の runbook・移行手順が「適用後はこうなる」と宣言しているなら、その状態を入力にして各経路をもう一度追う。今のデータで壊れるかだけを見ていると、前提が満たされた瞬間に消える指摘しか出ない。逆に、前提が満たされたことで初めて壊れる経路がいちばん見落とされる。
- **規約準拠** — リポジトリの `CLAUDE.md` / `AGENTS.md` / `CONTRIBUTING.md` 等に書かれた規約に反する箇所。**引用できる規則と、それを破っている行の両方を示せるときだけ挙げる。** lint が強制している項目は扱わない。
- **仕様照合**（仕様が渡されたときのみ） — 仕様が要求していて実装に無い/半端なもの、要求されていないのに入っているもの、実装したつもりでズレているもの。各指摘に該当する仕様の記述を引用する。

#### B群

- **言語の罠** — 差分の言語・フレームワークに固有の落とし穴。JS の falsy な 0・`==` の型強制・クロージャに捕まったループ変数、Python の可変デフォルト引数・遅延束縛、Go の nil map への書き込み・range 変数の捕捉、SQL インジェクション、タイムゾーン / DST のずれ、浮動小数の等価比較。ラッパ型（cache / proxy / decorator / adapter）を足したり変えたりしているなら、全メソッドが委譲先に向いているかを確かめる。レジストリやセッション経由で戻ると再入・再帰する。
- **コメントと実装の整合** — コメント・JSDoc・型定義・enum の注釈が、実装の現在の挙動と一致するか。コードを直したときにコメントだけ古いまま残った箇所。
- **履歴** — 変更箇所の `git blame` と、同じ箇所を過去に触った PR のレビューコメント。当時なぜそう書かれたか、過去に指摘されたことが再発していないか。
- **重複と残骸** — 新しいコードがリポジトリに既にあるものを再実装していないか。共有・ユーティリティモジュールと、変更の隣にあるファイルを Grep する。差分が置き去りにした dead code も。
- **深さ** — その修正が根本原因を正しい深さで直しているか、症状に絆創膏を貼っているか。共有基盤の上に特殊ケースが積まれていたら、深さが足りていない兆候。より単純で一般的な変更が下の機構側にあるなら、それを名指しする。

**完了条件**: 全レンズの結果が揃っている。

### 3. 候補を畳む

同じ行・同じ機構を指している候補は1件にまとめる。**残すのは失敗シナリオがいちばん具体的なもの。** 違う理由で同じ行を指しているだけなら、別件として両方残す。

畳まずに次へ回すと、同じ欠陥に採点者を何体も立てることになる。

**完了条件**: 候補の一覧に重複が無い。

### 4. 指摘ごとに採点する

残った候補それぞれについて、`blind-reviewer` サブエージェントを**1件に1つ**立てて並列に採点させる。発見した本人には採点させない。同時に立てるのは20体まで。超えるなら波を分ける。

採点者に渡すもの: 指摘の内容、対象、規約文書のパス、そして `references/rubric.md` のスケールを**逐語で**。カットラインの判断は採点者に見せず、次の4つだけを返させる。

1. **事実判定** — 主張は事実として正しいか（`正しい` / `一部正しい` / `誤り`）。**重要度は考慮しない。** 「本物だが些細」は `正しい`。
2. **確度スコア** — rubric のスケールで 0-100。**事実判定と整合させる。** 事実判定が `正しい` なら 50 を下回らない。`一部正しい` でも、正しい部分だけで対応が書けるなら同じ。25 以下は、本物かどうか確認できなかった場合に使う。
3. **対応** — この指摘に対応する具体的な変更を1つ書く。1行の差分でも「この文を消す」でもよい。**書けなければ「なし」と書く。**
4. **差分との因果** — `差分が作った` / `差分が既存の記述を偽にした` / `差分より前から同じ` のどれか。**差分が触った関数の中なら、変更されていない行のバグでも `差分が作った` に数える。**

**稀でも到達できるなら `正しい` 側に置く。** 並行性のレース、エラーハンドラ・コールドキャッシュ・欠けたオプショナルフィールドといった稀な経路、falsy な 0、境界の off-by-one、リトライ時の部分失敗 — その状態が現実に起こりうるなら本物として扱う。`誤り` を付けるのは、コードからそう構成できるときだけ。該当行を引用して事実と違うと示せる、型・定数・不変条件で不可能だと示せる、この差分の中で既に処理されている（ガードを引用する）、観測可能な影響のない純粋な様式、のいずれか。

「対応」を必須にするのは、同じ観測でも書き方で価値が変わるから。「ガードが一意性を保証できていない」は大きすぎて動けないが、「このコメントの主張が偽なので緩める」なら1分で終わる。前者のまま採点に回すと、直せるはずの指摘が「重要でない」として消える。

因果の判定を採点者に回すのは、**これが意図でいちばん甘くなる判定**だから。経緯を知っている側が「元からこうだった」と裁くと、差分が持ち込んだ問題まで既存扱いで落ちる。

**完了条件**: 全指摘に事実判定・確度・対応・因果が付いている。

### 5. 刈る

まず**捨てる**。順に当てて、1つでも該当したらそこで落とす。

1. 事実判定が `誤り` — 出さない。
2. **対応が「なし」** — 行動に変わらないものは指摘ではなく感想。
3. **因果が `差分より前から同じ`** — 差分が既存の記述を偽にした場合（コメント・ドキュメントが変更前は正しく変更後は誤り）は `差分が既存の記述を偽にした` なので残る。

残ったものに札を付ける。捨てる基準と札の基準は別物で、**確度は「出すかどうか」ではなく「どの札か」だけを決める**。

- `ask:` — 確度 80 以上。設計判断・仕様の確認を含み、作者の返答が要る。
- `IMO:` — 確度 50 以上。直したほうがよいと考えるが、作者の判断で見送ってよい。
- `nits:` — 確度 50 以上で、対応が数行に収まるもの。共通ヘルパとの重複、言い過ぎのコメント、命名。**軽いという理由では捨てない。** 直すのが一瞬なら出すほうが得。

確度 50 未満は、事実判定が `正しい` でも出さない。手順4の整合の指示に従っていればここに落ちるものはほぼ無いはずで、残っているなら採点が割れている合図として扱う。

残りが0件ならそう報告する。指摘を出すために基準を下げない。

**完了条件**: 残った指摘すべてに札が付き、捨てた件数が理由別に数えられている。

### 6. 返す

`ask:` → `IMO:` → `nits:` の順、同じ札の中では確度の高い順に並べる。各指摘に:

- 札（`ask:` / `IMO:` / `nits:`）
- `file:line`
- 何が起きるか（1文）
- 根拠（引用。規約・仕様を引くならその出典）
- 再現手順、または「この入力・状態でこの値になる」という具体
- **対応** — 何をどう変えるか。差分で書けるなら差分で
- 確度スコアと、出所のレンズ

末尾に、**捨てた件数と、落とした理由の内訳**（誤り / 対応なし / 既存 / 重複で畳んだ数）を1行で添える。呼び出し元が基準の妥当性を判断できるようにする。
