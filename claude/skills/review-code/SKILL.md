# review-code（盲検レビュー）

変更を**盲検**でレビューする。書いた本人の意図を知らない読み手として、**書いてあることだけ**から判断する。

狙うのは、静的チェックが緑になった後に残る欠陥 — **落ちない・型も通る・lint も通る、それでも静かに間違っている**もの。lint と型検査が拾えるものはそちらに任せ、ここでは探さない。

このスキルは1回のレビューで完結する。反復は呼び出し元の仕事なので、周回や停止条件はここでは扱わない。

## 入力

呼び出し元から受け取るのは次のものだけ。

- **対象** — ファイルの一覧、または差分の取り方（`git diff <fixed-point>...HEAD` など）
- **除外** — レビュー対象外のパス（`docs/` など）
- **仕様**（あれば） — issue / PRD の本文。取得済みのテキストで受け取る
- **追加観点**（あれば） — 今回とくに見てほしい点
- **判定済み台帳**（あれば） — 既に却下された指摘。同じものを再提示しない

対象が渡されていなければ、何をレビューするのかを聞いてから始める。

判断の材料は、この入力とリポジトリから自分で読んだコードに限る。**実装の経緯や意図の説明を持っている場合も、レビューには使わない。** それを混ぜた時点で、書いた本人と同じ盲点を引き継ぐことになる。盲検が崩れるとこのスキルの値打ちは丸ごと消える。

## 手順

### 1. 対象を確定する

差分の取り方を渡されたなら実行して、対象ファイルの一覧を出す。除外を適用する。

参照が解決しない、差分が空、といった失敗はここで止める。レンズを撒いた後に発覚させない。

**完了条件**: レビュー対象のファイルが列挙できている。

### 2. レンズを並列に当てる

下の各レンズについて `blind-reviewer` サブエージェントを1つ立て、**1メッセージにまとめて**投げる。各エージェントには対象・除外・仕様・追加観点・台帳と、そのレンズの担当範囲を渡す。

レンズを分けるのは、1人に全部見せると見落としが1人分の偏りに揃うから。担当を分けた方が網が広がる。

各レンズには変更ファイルを**全部**渡す。行数の少ないファイル（フック・薄いラッパ・設定）は流し読みされやすいが、同じ差分の中の兄弟ファイルと食い違っている、共通ヘルパを迂回している、といった指摘はそこに出る。

- **挙動** — 差分だけを読み、大物を狙う。各出力（値・イベント・戻り値・状態）について、名前・型・コメントが宣言している意味を導き、実際にその意味の値になるかを実行経路で追う。定数しか返さないフィールド、意図しない経路で発火するイベント、名乗りと実挙動がズレた戻り値。
  - **現在の状態だけでなく、この変更が意図している終了状態からも推論する。** 差分やリポジトリ内の runbook・移行手順が「適用後はこうなる」と宣言しているなら、その状態を入力にして各経路をもう一度追う。今のデータで壊れるかだけを見ていると、前提が満たされた瞬間に消える指摘しか出ない。逆に、前提が満たされたことで初めて壊れる経路がいちばん見落とされる。
- **コメントと実装の整合** — コメント・JSDoc・型定義・enum の注釈が、実装の現在の挙動と一致するか。コードを直したときにコメントだけ古いまま残った箇所。
- **規約準拠** — リポジトリの `CLAUDE.md` / `AGENTS.md` / `CONTRIBUTING.md` 等に書かれた規約に反する箇所。文書に書かれていることだけを根拠にする。lint が強制している項目は扱わない。
- **履歴** — 変更箇所の `git blame` と、同じ箇所を過去に触った PR のレビューコメント。当時なぜそう書かれたか、過去に指摘されたことが再発していないか。
- **仕様照合**（仕様が渡されたときのみ） — 仕様が要求していて実装に無い/半端なもの、要求されていないのに入っているもの、実装したつもりでズレているもの。各指摘に該当する仕様の記述を引用する。

**完了条件**: 全レンズの結果が揃っている。

### 3. 指摘ごとに採点する

レンズが返した指摘それぞれについて、`blind-reviewer` サブエージェントを**1件に1つ**立てて並列に採点させる。発見した本人には採点させない。

採点者に渡すもの: 指摘の内容、対象、規約文書のパス、そして `references/rubric.md` のスケールを**逐語で**。カットラインの判断は採点者に見せず、次の3つだけを返させる。

1. **事実判定** — 主張は事実として正しいか（`正しい` / `一部正しい` / `誤り`）。**重要度は考慮しない。** 「本物だが些細」は `正しい`。
2. **確度スコア** — `references/rubric.md` のスケールで 0-100。
3. **対応** — この指摘に対応する具体的な変更を1つ書く。1行の差分でも「この文を消す」でもよい。**書けなければ「なし」と書く。**

「対応」を必須にするのは、同じ観測でも書き方で価値が変わるから。「ガードが一意性を保証できていない」は大きすぎて動けないが、「このコメントの主張が偽なので緩める」なら1分で終わる。前者のまま採点に回すと、直せるはずの指摘が「重要でない」として消える。

**完了条件**: 全指摘に事実判定・確度・対応が付いている。

### 4. 刈る

まず**捨てる**。順に当てて、1つでも該当したらそこで落とす。

1. 事実判定が `誤り` — 出さない。
2. **対応が「なし」** — 行動に変わらないものは指摘ではなく感想。
3. **差分が作った問題ではない** — 差分より前から同じコードが同じ挙動をしているなら落とす。ただし**差分が既存の記述を偽にした**場合（コメント・ドキュメントが変更前は正しく変更後は誤り）は残す。

残ったものに札を付ける。捨てる基準と札の基準は別物で、**確度は「出すかどうか」ではなく「どの札か」だけを決める**。

- `ask:` — 確度 80 以上。設計判断・仕様の確認を含み、作者の返答が要る。
- `IMO:` — 確度 50 以上。直したほうがよいと考えるが、作者の判断で見送ってよい。
- `nits:` — 確度 50 以上で、対応が数行に収まるもの。共通ヘルパとの重複、言い過ぎのコメント、命名。**軽いという理由では捨てない。** 直すのが一瞬なら出すほうが得。

確度 50 未満は、事実判定が `正しい` でも出さない。裏が取り切れていないものを混ぜると、正しい指摘まで巻き添えで読まれなくなる。

残りが0件ならそう報告する。指摘を出すために基準を下げない。

### 5. 返す

`ask:` → `IMO:` → `nits:` の順、同じ札の中では確度の高い順に並べる。各指摘に:

- 札（`ask:` / `IMO:` / `nits:`）
- `file:line`
- 何が起きるか（1文）
- 根拠（引用。規約・仕様を引くならその出典）
- 再現手順、または「この入力・状態でこの値になる」という具体
- **対応** — 何をどう変えるか。差分で書けるなら差分で
- 確度スコアと、出所のレンズ

末尾に、**捨てた件数と、落とした理由の内訳**（誤り / 対応なし / 既存）を1行で添える。呼び出し元が基準の妥当性を判断できるようにする。
