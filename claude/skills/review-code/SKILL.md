# review-code（盲検レビュー）

変更を**盲検**でレビューする。書いた本人の意図を知らない読み手として、**書いてあることだけ**から判断する。

狙うのは、静的チェックが緑になった後に残る欠陥 — **落ちない・型も通る・lint も通る、それでも静かに間違っている**もの。lint と型検査が拾えるものはそちらに任せ、ここでは探さない。

このスキルは1回のレビューで完結する。反復は呼び出し元の仕事なので、周回や停止条件はここでは扱わない。

## 入力

呼び出し元から受け取るのは次のものだけ。

- **対象** — ファイルの一覧、または差分の取り方（`git diff <fixed-point>...HEAD` など）
- **除外** — レビュー対象外のパス（`docs/` など）
- **仕様**（あれば） — issue / PRD の本文。取得済みのテキストで受け取る
- **追加観点**（あれば） — 今回とくに見てほしい点
- **判定済み台帳**（あれば） — 既に却下された指摘。同じものを再提示しない

対象が渡されていなければ、何をレビューするのかを聞いてから始める。

判断の材料は、この入力とリポジトリから自分で読んだコードに限る。**実装の経緯や意図の説明を持っている場合も、レビューには使わない。** それを混ぜた時点で、書いた本人と同じ盲点を引き継ぐことになる。盲検が崩れるとこのスキルの値打ちは丸ごと消える。

## 手順

### 1. 対象を確定する

差分の取り方を渡されたなら実行して、対象ファイルの一覧を出す。除外を適用する。

参照が解決しない、差分が空、といった失敗はここで止める。レンズを撒いた後に発覚させない。

**完了条件**: レビュー対象のファイルが列挙できている。

### 2. レンズを並列に当てる

下の各レンズについて `blind-reviewer` サブエージェントを1つ立て、**1メッセージにまとめて**投げる。各エージェントには対象・除外・仕様・追加観点・台帳と、そのレンズの担当範囲を渡す。

レンズを分けるのは、1人に全部見せると見落としが1人分の偏りに揃うから。担当を分けた方が網が広がる。

- **挙動** — 差分だけを読み、大物を狙う。各出力（値・イベント・戻り値・状態）について、名前・型・コメントが宣言している意味を導き、実際にその意味の値になるかを実行経路で追う。定数しか返さないフィールド、意図しない経路で発火するイベント、名乗りと実挙動がズレた戻り値。
- **コメントと実装の整合** — コメント・JSDoc・型定義・enum の注釈が、実装の現在の挙動と一致するか。コードを直したときにコメントだけ古いまま残った箇所。
- **規約準拠** — リポジトリの `CLAUDE.md` / `AGENTS.md` / `CONTRIBUTING.md` 等に書かれた規約に反する箇所。文書に書かれていることだけを根拠にする。lint が強制している項目は扱わない。
- **履歴** — 変更箇所の `git blame` と、同じ箇所を過去に触った PR のレビューコメント。当時なぜそう書かれたか、過去に指摘されたことが再発していないか。
- **仕様照合**（仕様が渡されたときのみ） — 仕様が要求していて実装に無い/半端なもの、要求されていないのに入っているもの、実装したつもりでズレているもの。各指摘に該当する仕様の記述を引用する。

**完了条件**: 全レンズの結果が揃っている。

### 3. 指摘ごとに採点する

レンズが返した指摘それぞれについて、`blind-reviewer` サブエージェントを**1件に1つ**立てて並列に採点させる。発見した本人には採点させない。

採点者に渡すもの: 指摘の内容、対象、規約文書のパス、そして `references/rubric.md` のスケールを**逐語で**。カットラインの判断は採点者に見せず、点数だけ付けさせる。

**完了条件**: 全指摘に 0-100 の点が付いている。

### 4. 刈る

**80 未満を捨てる。** 判断を挟まない。

残りが0件ならそう報告する。指摘を出すために線を下げない。

### 5. 返す

点数の高い順に並べて返す。各指摘に:

- `file:line`
- 何が起きるか（1文）
- 根拠（引用。規約・仕様を引くならその出典）
- 再現手順、または「この入力・状態でこの値になる」という具体
- 信頼度スコア
- 出所のレンズ

末尾に、**捨てた件数と、その中で最高だった点数**を1行で添える。呼び出し元がカットラインの妥当性を判断できるようにする。
