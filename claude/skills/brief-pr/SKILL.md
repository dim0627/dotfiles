# brief-pr

レビュアーがPRを読み始める前に渡す**ブリーフ**を作る。中身は「何を・なぜ」、変更の**地図**、コードを読む**前提**の3つ。ブリーフを読んでからコードを読むほうが、いきなりコードを読むより速く正しく理解できれば、役目を果たしている。

ブリーフは理解の下地で、判断はレビュアーに残す。品質・性能・規約・作者の進め方（PRの分け方・マージ順）の評価はブリーフに入れない。評価が混ざると、レビュアーはまずその真偽を確かめることになり、コードより読むのが重くなる。

ブリーフの全文は**出典**か**推測**のどちらかに属する。出典は引用元（PR本文・チケット・コミット・`file:line`）を添え、推測は推測と明記する。意図が書かれていない箇所を推測で埋めて断定すると、レビュアーは作者と違う前提でコードを読むことになる。

結果は Artifact（claude.ai 上の非公開ページ）で返す。PR・チケットへの書き込みはしない。

## 入力

PRのURLか番号。無ければどのPRか聞いてから始める。

## 手順

### 1. 意図を集める

```bash
gh pr view <PR> --json url,headRefOid,title,body,author,baseRefName,headRefName,commits,files,comments,reviews,closingIssuesReferences
gh pr checks <PR>
```

- **本文に出てくるPR番号・issue・チケットを1段たどる**。「Follow-up to #N」の前段PRには、今回の変更が埋めようとしている穴が書かれていることが多い。別チケットで削除や置き換えが決まっているコードも、ここで分かる
- Linear は PR に linkback コメント（author `linear`）でチケット本文を貼る。チケット上のコメント・議論まで要るときは Linear のツールで取る

**完了条件**: 本文から参照されているPR・チケットを全件読んだか、読めなかったものを理由つきで列挙できている。

### 2. PRのコードを手元に置く

呼び出し元は差分に出てこないため、リポジトリ全体を PR head の状態で読む。

1. ローカル clone を探す（カレントリポジトリ、または `ghq list -p | grep <repo>`）。無ければ clone してよいかユーザーに聞く。断られたら差分だけで進め、地図に「呼び出し元は未確認」と書く
2. 作業ツリーを動かさずに head を取る:
   ```bash
   git fetch origin pull/<N>/head:refs/remotes/pr/<N> <base>
   ```
3. 以降は `git show pr/<N>:<path>` と `git grep <pattern> pr/<N> -- <dir>` で PR 時点のコードを読む

**完了条件**: `pr/<N>` の ref からファイルを読めて、grep も通る。

### 3. 地図を描き、前提を拾う

変更されたシンボルごとに、**入口（ルート・ハンドラ・公開API・ジョブ等）から変更箇所までの呼び出し経路**をたどる。上方向は `git grep` で呼び出し元を、下方向は変更箇所が呼んでいる先を読む。

- 経路をツリーで書き、変更ノードに印を付ける（変更前→変更後の振る舞いを一言添える）
- コメント・JSDoc だけの変更、リネーム、生成物、フォーマット、テストは付随的な変更として分けておく

地図を描きながら、**前提**を拾う。前提とは、知らずに読むとコードを読み違える事実のこと。例えば:

- 値の出どころが見た目と違う（「ランクは参加中の行でなく、精算の記録から読む」）
- 変更箇所が差分の外の振る舞いに依存している（「精算は参加者ゼロの日に行を書かない」）
- 近く消える予定のコード（別チケットで削除が決まっている等）。軽く読めば十分だと添える

本文の説明は、コードと合っているのを確かめてから前提として使う。合っていなくて読み違いにつながるものは、コードの実際のほうを前提として書く。

**完了条件**: 変更ファイルが全部、どれかの経路に載っているか付随的な変更に分類されている。拾った前提がそれぞれ出典か `file:line` を持っている。

### 4. ブリーフを Artifact で返す

ブリーフを HTML ページに書き、Artifact として公開する。ファイルはスクラッチパッドの `brief-pr-<repo>-<N>.html`。同じセッションで同じPRを作り直すときは同じパスで再公開し、URL を保つ。

ページの節は次の順。

- **ヘッダ**: PR番号・タイトル（PRへのリンク）・作者・base ← head・CI の結果
- **何を・なぜ**: 一文。出典つき
- **変更の地図**: 入口→変更ノードのツリー。変更ノードを強調し、変更前→変更後の振る舞いを一言添える。付随的な変更は末尾にまとめる
- **読む前に知っておくこと**: 手順3で拾った前提。1項目1〜2文
- **聞くこと**: コードと出典を読んでも意図が分からず、作者に確かめないと理解が進まない箇所。無ければ節ごと省く

分量は前提の数で決まる。差分より短く読めるページにする。

ページで守ること:

- `file:line` は PR head のコミットに固定した GitHub リンクにする（`<repo URL>/blob/<headRefOid>/<path>#L<line>`）。ブランチ名で張ると、後の push で行がずれる
- 推測は出典つきの記述と見た目で区別する（ラベル・色など）

会話には、Artifact のリンク、「何を・なぜ」の一文、聞くことの件数だけを返す。
