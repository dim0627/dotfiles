# brief-pr

レビュアーがPRを読み始める前に渡す**ブリーフ**を作る。目的は理解の下地を作ること。読んでいて気づいた疑問は「聞くこと」に回す。

ブリーフの全文は**出典**か**推測**のどちらかに属する。出典は引用元（PR本文・チケット・コミット・`file:line`）を添え、推測は推測と明記する。意図が書かれていない箇所を推測で埋めて断定すると、レビュアーは作者と違う前提でコードを読むことになる。

結果は会話に返す。PR・チケットへの書き込みはしない。

## 入力

PRのURLか番号。無ければどのPRか聞いてから始める。

## 手順

### 1. 意図を集める

```bash
gh pr view <PR> --json title,body,author,baseRefName,headRefName,commits,files,comments,reviews,closingIssuesReferences
gh pr checks <PR>
```

- **本文に出てくるPR番号・issue・チケットを1段たどる**。「Follow-up to #N」の前段PRには、今回の変更が埋めようとしている穴が書かれていることが多い。前段PRが主張していた内容も、手順3の照合対象に加える
- Linear は PR に linkback コメント（author `linear`）でチケット本文を貼る。チケット上のコメント・議論まで要るときは Linear のツールで取る。取れなければ「本文のみ参照」と明記する
- CI の結果と、本文にある「ローカルで未検証」等の申告を控えておく

**完了条件**: 本文から参照されているPR・チケットを全件読んだか、読めなかったものを理由つきで列挙できている。

### 2. PRのコードを手元に置く

呼び出し元は差分に出てこないため、リポジトリ全体を PR head の状態で読む。

1. ローカル clone を探す（カレントリポジトリ、または `ghq list -p | grep <repo>`）。無ければ clone してよいかユーザーに聞く。断られたら差分だけで進め、地図に「呼び出し元は未確認」と書く
2. 作業ツリーを動かさずに head を取る:
   ```bash
   git fetch origin pull/<N>/head:refs/remotes/pr/<N> <base>
   ```
3. 以降は `git show pr/<N>:<path>` と `git grep <pattern> pr/<N> -- <dir>` で PR 時点のコードを読む

**完了条件**: `pr/<N>` の ref からファイルを読めて、grep も通る。

### 3. 地図を描き、照合する

変更されたシンボルごとに、**入口（ルート・ハンドラ・公開API・ジョブ等）から変更箇所までの呼び出し経路**をたどる。上方向は `git grep` で呼び出し元を、下方向は変更箇所が呼んでいる先を読む。

- 経路をツリーで書き、変更ノードに印を付ける（変更前→変更後の振る舞いを一言添える）
- 変わった振る舞いに依存している周辺も見る。そこへ遷移・呼び出しをしている他の箇所、状態の初期値、ガード、キャッシュなど。変更自体は正しくても、周辺の前提で意味が変わる箇所がここに出る
- 変わった振る舞いを検証するテストがあるか探す。CI が緑でも、該当テストが無ければ未検証として扱う
- コメント・JSDoc だけの変更、リネーム、生成物、フォーマットは付随的な変更として分けておく

地図を描きながら、手順1で集めた主張（今回と前段の本文、チケットの要件）を1つずつコードと**照合**する。

**完了条件**: 変更ファイルが全部、どれかの経路に載っているか付随的な変更に分類されている。振る舞いについての主張がそれぞれ「一致（`file:line`）」「不一致」「未確認」のどれかになっている。

### 4. ブリーフを返す

```
## PR #<N> ブリーフ

### 何を・なぜ
<一文。出典つき>

### 意図の出典
- <チケット / 前段PR / 本文>: <要旨>（本文と実装が食い違っていればここで書く）

### 変更の地図
<入口→変更ノードのツリー。付随的な変更は末尾に一行で>

### 押さえる点
- <周辺の前提で意味が変わる箇所、依存している呼び出し元、照合の結果>

### 聞くこと
1. <意図が読めない箇所・不一致・テストが無い振る舞い>
<このPRが持ち込んだものではない既存の問題は、分けて最後に書く>
```

小さなPRなら節を省いてよい。ただし「何を・なぜ」と地図は省かない。
