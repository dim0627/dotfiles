# write-plan（plan を書く）

plan は、spec（何を・なぜ作るか）と実装のあいだに置く技術設計の文書。読み手は主に**実装するエージェント**と、plan に書かれた判断を確かめる人間。

目指すのは、**この plan を渡せば誰が実装しても、外から見える振る舞いがほぼ同じになる** plan。関数の分け方・シグネチャ・命名までは揃えなくてよい。そこは実装者に任せる。決めきるのは境界、つまりデータ・API・振る舞い・副作用・移行。

Claude Code の plan mode が出す作業手順のメモとは別物。あちらは「何から手を付けるか」の列で、こちらは「何を決めたか」の記録。

## 0. プロジェクトの規約を先に探す

次の場所に plan の書き方の規約があれば、**それに従い、このスキルの既定より優先する**。

- `CLAUDE.md` / `AGENTS.md`
- `.claude/skills/` の中の plan・design doc・spec 用のスキル
- `docs/README.md` や `docs/plans/` の README

規約が節の構成だけを決めていて、下の必須項目の一部に触れていない場合は、規約の構成の中で補う。規約と矛盾する場合は規約を取る。

置き場所とファイル名の規約が無ければ、`docs/plans/YYYY-MM-DD-kebab-case-title.md` に置く。書く言語は、規約が無ければユーザーとの会話の言語にする。

**完了条件**: 従う規約（または既定）と、plan の置き場所が決まっている。

## 1. 書くかどうかを決める

次のどれかに当たるなら、plan を書かずに直接実装してよいとユーザーに提案する。

- 書くより実装した方が早い
- 選択肢が実質1つしかなく、検討した代替案が書けない
- 振る舞いを変えないリファクタリング

**完了条件**: 書くと決まっている。書かない提案をしたなら、ユーザーの返事を受けている。

## 2. 材料を集める

- **spec**: チケット・issue・PRD・会話で決まったこと。無ければ、why と受け入れ条件をユーザーに確かめる。spec が無いまま設計を始めると、推測した要件の上に設計が乗る
- **今のコード**: 触るモジュール、似た既存実装、既存の規約（エラーの返し方・権限・ページング・ログ）。既存の handler がどうしているかは、plan で明示しない限り実装者が真似る既定になる
- **プロジェクトの不変条件・規約のドキュメント**（あれば）

**完了条件**: why と受け入れ条件が言え、触る範囲の既存の振る舞いを読み終えている。

## 3. 必須の節を書く

次の6つを必ず置く。**該当しない項目も消さずに「なし」と書く。** 書き忘れと、検討して不要と判断したことを区別するため。

### Context

- なぜやるか、何を解くか
- spec へのリンク（チケット ID・URL）
- 現状のどこが問題か。現状のコードは、ファイルパスと関数名・型名で示す。行番号はすぐずれる

### Goals / Non-goals

- Goals: この変更で満たすこと。spec の要件・受け入れ条件が、Goals か Non-goals のどちらかに必ず入っている
- Non-goals: ゴールになり得たが、意図的に外したもの

### Design

外から見える決定を、該当するものすべて書く。

- **データ**: テーブル・カラム・型・制約・既定値・インデックス
- **API の契約**: ルート、リクエストとレスポンスの形、ステータスコードとエラー、権限
- **振る舞い**: 境界値・空・重複・同時実行・存在しない対象・状態ごと（公開中か、期限切れか）の扱い。**具体例で書く**
- **副作用**: 書き込み、通知、ジョブ、キャッシュ、外部 API 呼び出し、ログ・監査
- **既存とのつながり**: どの既存の規約・実装に揃えるか、どこで外れるか

決定は文と表で書く。コードは、型の形やシグネチャを示すのに要る最小限だけ引く。コードを貼り付けた plan は決定が埋もれて読めなくなり、実装者に任せるはずの中身まで縛る。

### Decisions

検討した代替案と、選ばなかった理由。「何もしない」も案に含める。

| 選んだもの | 選ばなかったもの | 理由 |
|---|---|---|

代替案が1つも書けないなら、手順1に戻って plan が要るかを見直す。

### Risks and rollout

- 認証・認可、外部入力の検証
- データ移行・バックフィル・後方互換（既存のデータ、古いクライアント、処理中の状態）
- ロールアウトの順序（デプロイ順、フラグ）と切り戻しの手順
- 観測: 壊れたときにどう気づくか

### Verification and open questions

- **Verification**: 何が確かめられたら完成か。spec の受け入れ条件ごとに確かめ方を書く。型チェックや lint を流すだけでは確かめたことにならない。可能なら、実装を壊したら落ちるテストを示す
- **Open questions**: まだ決めていないこと。本文の未決（TODO・TBD など）は全部ここに集める。各項目に推奨案を添える

## 4. 任意の節

必要なときだけ足す。

- 変更するファイルの一覧
- 実装の順序（PR の分け方、同じ PR に入れる必要があるもの）
- 図（データの流れ、状態遷移）

## 5. 見直す

書き終えたら、実装者の立場で plan を読み直す。

1. **実装者が推測する決定を探す。** Design の各項目について、根拠が「plan に書いてある」か「既存のコード・規約が決めている」かを確かめる。どちらでもない決定は、Design に書き足すか Open questions に移す。いちばん見落とすのは「書いてないから何もしない」既定値で、フラグは無し、監査は残さない、状態に関係なく操作できる、などを実装者は黙って選ぶ。意図して選んだなら明記する
2. **長さを見る。** 目安は 1〜3 ページ。超えるなら、コードの貼り付けか、別の plan に分けるべき範囲が混ざっていないかを疑う

**完了条件**: 必須の6節がそろい、根拠の無い外から見える決定が Design にも Open questions にも残っていない。

## 6. 渡す

plan のパスと、Open questions の一覧をユーザーに返す。Open questions はユーザーが判断する項目なので、plan を開かなくても答えられる形で並べる。

plan は出荷まで更新し、出荷後は書き換えない。書いた時点の判断の記録として残す。現行のルールは plan ではなく、コードとプロジェクトの規約ドキュメントに置く。
