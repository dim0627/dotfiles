# 観測手段リファレンス（ユーザー報告の切り分け用）

**必要になった節だけ読む。**

## 共通原則

- **名前を決め打ちしない。** プロジェクト名・テーブル名・リソース名は必ず一覧を取得して実在する値から選ぶ。決め打ちの最悪の壊れ方は、クエリが0件を返して**実際には起きている不具合を「発生していない」と報告する**こと
- **取れなかったものは「取得失敗」と書く。** 観測の欠落自体が報告すべき情報
- **絶対値より比率。** 「エラー6,000件」は多いのか少ないのか判定できない。**規模は必ず分母とセットで書く**
- **具体的な取得手段（接続方法・ダッシュボード・テーブル名・データソースID）はプロジェクト側に蓄積されていることが多い。** 汎用の手順を組む前に `MEMORY.md` / `CLAUDE.md` / `docs/` を見る

---

## 症状の出所を探す

**画面に出ていたものを、コードベース上の固有名詞に変換する。** これが割れると以降が全部速い。

```bash
# 表示文字列から。文言リソースは言語別ディレクトリに散る
grep -rIn '<画面に出ていた文字列>' . --exclude-dir={.git,node_modules,build,Pods,Library}

# 見つからないとき: 文言が画像に焼き込まれている可能性。ファイル名で探す
find . -not -path '*/.git/*' -not -path '*/Library/*' \
  \( -iname '*error*' -o -iname '*fail*' -o -iname '*empty*' \) \
  \( -iname '*.png' -o -iname '*.webp' -o -iname '*.json' -o -iname '*.xml' \) | head -30
```

**画像アセットは実際に開いて中身を見る。** ファイル名が症状と一致していても、別の画像であることがある。

見つけた名前の**使用箇所**へ移動する。そこが症状の生まれる場所。

多言語対応がある場合、**症状の言語のリソースだけを見て終わらせない**（キー名で引き直す）。

## 関係するリポジトリの特定

クライアントの不具合はサーバのリポジトリには無い。カレント以外を必ず確認する。

```bash
ls ..                                      # 兄弟ディレクトリ
git -C ../<repo> branch --show-current     # どのブランチが checkout されているか
git -C ../<repo> log -1 --format='%h %ad %s' --date=short
```

**checkout が報告バージョンより古いことは珍しくない。** 差分を控え、「読んだのは報告版そのものではない」と報告に明記する。該当バージョンのタグ／ブランチが手元に無いなら、それ自体が「取れなかったもの」。

## エラートラッカー

**プラットフォームごとに別物であることを前提にする。** サーバは Sentry でもモバイルは Crashlytics だけ、ということが普通にある。**片方で0件だったことを「エラーが無かった」と読まない。**

まず**報告経路の実装を読む**（`reportError` / `recordException` / `captureException` のラッパ）。どこへ送っているか、サンプリングやフィルタが掛かっていないかを確認する。ここを飛ばすと、証拠の不在を誤読する。

### 致命 / 非致命の区別

**「クラッシュ記録が無い」は「エラーが無い」ではない。** アプリが落ちない不具合は**非致命（non-fatal / handled）**として記録される。コンソールの既定表示が致命だけのことがあるので、非致命を明示的に見る。

### コンソールに入れないとき

エラートラッカーは**データウェアハウスへエクスポートされていることがある**（Crashlytics → BigQuery など）。SQL で引けると、コンソールでは面倒な集計（ユーザー単位の突合、機種別分布、比率の時系列）が一気に取れる。プロジェクト側の蓄積に接続情報があることが多い。

- **リアルタイム系と日次系でテーブルが分かれ、遅延が違う**ことがある。直近の事象は遅延の小さい方から引く
- **エクスポート開始時期がアーティファクトになる。** 生件数は導入時期に合わせて立ち上がるので、「急増」に見える。**必ず全体に対する比率で見る**
- **難読化（R8 / ProGuard / minify）でファイル名・行番号が潰れる。** マッピングが無いならソース行に対応づけられない ＝「取れなかったもの」

### 報告者本人の特定

**アカウントID・端末・アプリ版で突合できると確度が一段上がる。** ユーザー識別子が記録されているなら、報告時刻の前後で本人のイベントだけを引く。ここが取れたら、それが最も強い証拠になる。

取るもの: **例外の型・実メッセージ文字列・発生時刻・端末 / OS / アプリ版・スタックの最上位フレーム**。**例外チェーンは下（原因側）まで**読む — 表層の型だけでは原因クラスが決まらない。

## 規模と分母

**「この1人の話か」を出さない報告は、引き渡し先が優先度を決められない。**

取るもの:

1. **総件数**（期間を明示）
2. **影響ユーザー数**（件数ではなくユニーク数。1人が100回踏むのと100人が1回ずつは全く別）
3. **1人あたりの回数** = 1 ÷ 2。**「一度きりの事故」か「何度も踏んでいる」かが分かれる**
4. **分母** — 対象プラットフォームのアクティブユーザー数、または対象機能の実行回数。アプリ内のデータベースから取ることになる
5. **時系列** — 新規か慢性か。**特定のリリースを跨いで段差があるか**

⭐ **到達ユーザー率と、1回あたりの失敗率は別の指標。** 「利用者の10%が2週間のうちに1度は踏む」と「1回の実行あたり0.1%が失敗する」は同じ事象の両面で、**片方だけ書くと優先度が大きくブレる**。両方出せないなら、出した方がどちらの意味かを明記する。

**分母の落とし穴**: 識別子の粒度がズレる（インストール数 ⇔ アカウント数 ⇔ 端末数は1:1ではない）、プラットフォーム値の表記ゆれ、複数端末を持つユーザーの重複計上。**ズレの向き（過大か過小か）を書く。**

## 既報を探す

**同じ症状で過去にチケットが立っていることが非常に多い。** ここを飛ばすと、既に判明している原因を再発見するのに時間を使う。

- 症状の言葉・コード上の固有名詞・アセット名・例外の型で、**チケットとPRの両方**を検索する。クローズ済み・アーカイブ済みも含める
- コード中のコメントに書かれたチケット番号（`// See PGR-1234`）は**過去に同じ場所が壊れた証拠**。必ず本文を読む
- ⭐ **「修正済み」を「もう起きない」と読まない。** 修正 PR を開いて**何を捕まえて何を捕まえていないか**まで見る。よくある形:
  - 例外メッセージの**文字列マッチ1本**だけで分岐していて、別の文言は素通りする
  - 特定の再現手順だけを潰していて、同じ壊れ方の別経路が残っている
  - 片方のプラットフォームだけ直っている
- **未着手のまま残っているチケット**も探す。今回の報告がそれの再来であることがある

## 対向実装との比較

**同じ機能の別実装を読む。** iOS ⇔ Android、v1 ⇔ v2、web ⇔ ネイティブ、旧経路 ⇔ 新経路。

**片方だけ既に直っていることが多い。** その場合、対向実装が**そのまま修正の設計図**になる（何を防御しているかを列挙すれば、欠けている側の不足がそのまま出る）。

- 対向側で同じ症状のチケットが**過去に**クローズされていないか
- 対向側にあってこちら側に無い防御は何か（エラー時の状態リセット、状態のスコープ、キャッシュの破棄、タイムアウト、リトライ）
- 「両方に同じ穴がある」なら、それは**共有ロジックか仕様側**の問題

## ユーザー申告の裏取り

申告は**観測ではなく記憶**。実データで確かめられる項目は必ず確かめ、**食い違ったら食い違いごと報告する**。

| 申告 | 裏の取り方 | よくあるズレ |
|---|---|---|
| 「最新版です」 | 実データのアプリ版 | 数バージョン前のことがある |
| 「毎回起きます」 | 実イベントの件数と間隔 | 数回のことがある |
| 「直りません」 | 事象の継続時間・再発間隔 | 「毎回再発する」を「復帰しない」と表現している |
| 「再起動しても駄目」 | 再起動を跨いで発生しているか | 実際は試していないことがある |
| 端末名・OS | 実データの型番 | 通称と型番が違うだけで一致していることも多い |

**ズレていても報告の価値は落ちない。** ズレの中身が原因クラスを絞ることがある（例:「毎回」が実は「特定の条件のときだけ」）。

---

## 原因クラスの引き出し

| クラス | 典型症状 | 決定的な観測 |
|---|---|---|
| 状態が解除されない | 一度出たら操作しても戻らない。再起動やリロードで直る | 状態を立てる箇所と**解除する箇所**の非対称。解除側に早期 return やガードが無いか |
| キューやロックの詰まり | 最初の1回で止まり、以降その機能全体が反応しない | 進める経路が**成功時にしか無い**。エラー・タイムアウト・キャンセルの経路の有無 |
| ライフサイクル競合 | 再現手順が定まらない。特定の操作を素早くやると出る | 破棄と使用が別スレッド／別タイミング。破棄後に使う経路 |
| データ起因 | 特定のユーザー・特定のレコードだけ失敗 | 失敗した入力の共通点。正常なレコードとの差分 |
| 入稿・設定値起因 | 特定のコンテンツでだけ再現 | そのコンテンツのレコードを直接読む。欠損・範囲外・単位違い |
| バージョンスキュー | 特定のアプリ版だけ、または特定の組み合わせで失敗 | 版別の発生率。サーバ側の変更時刻との突合 |
| キャッシュの毒 | 一度失敗すると**同じ対象だけ**永久に失敗する。他は正常 | 失敗時にキャッシュを破棄しているか |
| 端末・環境固有 | 少数の機種・OS に偏る | 機種／OS／ベンダ分布。**偏っていなければこのクラスは棄却できる** |

**「特定の機種で報告された」を「機種固有」と読まない。** 分布を取るまでは、単にその機種のユーザーが多いだけかもしれない。**分布が散っていれば、それはアプリ側のロジックの問題**という強い証拠になる。

**「コードを読んだら筋が通る」を根拠にしない。** 通る筋は複数ある。**どの経路を実際に踏んだかは、実データでしか決まらない。** 決まらないなら「上流は未特定」と書く。
