**1件のユーザー報告の切り分け。** 原因クラスの特定と、担当チームに引き渡せる根拠の提示まで。修正は含まない。

**これじゃないとき**

- **アラートが鳴った / 全体が同時に壊れている** → `investigate-alert`。分かれ目は「インフラかバグか」ではなく「全体障害か、個別報告か」
- **手元で再現できる、または再現ループを作れる** → `diagnosing-bugs`。あちらは「タイトなフィードバックループを作る」が本体で、それが作れるならこのスキルより強い
- このスキルは **ループが原理的に作れない不具合**用 — 他人の端末でしか出ない / 本番のデータでしか出ない / 慢性で非決定的 / 報告者にもう連絡がつかない

## 原則

**この形である理由**

1. **観測は人間の選択を待たない。** 観測面は固定（実データ / 規模 / 既報 / 対向実装）なので、聞くまでもなく全部並列で投げる
2. **エージェントは反証者。** 「支持する証拠を探せ」ではなく「**反証しろ。できなかった場合だけ支持と報告しろ**」。偽陽性（それらしいコードを犯人に仕立てる）が最も高くつく
3. **返り値は契約で固定する。** 生の数字を持ち帰らせない。統合がメインに乗ると会話が止まる
4. **時刻ではなく症状の見た目から入る。** ユーザー報告に「発生時刻とデプロイの相関」を期待しない。慢性の不具合が最も多く、そこに時間軸は無い
5. **「1人の話か」を必ず出す。** 規模の分からない報告は優先度がつけられず、放置か過剰対応のどちらかになる

**そのまま信じないもの**（以降この4語をこの意味で使う）

- **証拠の不在** — 不在の証拠ではない。0件もログの不在も「取れなかった」であって「無かった」ではない。**特にクラッシュ記録が無いことは、非致命エラーが無いことを意味しない**
- **アーティファクト** — 欠落や異常値に見えるものの多くは、取得窓・集計単位・**ログ基盤の導入時期**が作る。窓と粒度を変えても同じ結論になるかで切り分ける
- **人為** — 症状の裏に運用操作や手動のデータ変更があることがある。ログ側からは自然発生と区別できない
- **ユーザーの言葉** — 「最新版です」「毎回です」「直りません」「再起動しても駄目」は**観測ではなく記憶**。実データで裏を取れる項目は必ず取る（アプリ版・端末・発生時刻は大抵取れる）。**食い違ったら、食い違いごと報告する**

## 手順

### 0. 報告の読み取り（コードは読まない）

貼られたものから **症状の見た目（画面に何が出たか）/ 直前の操作 / 再現条件 / 端末・OS・アプリ版 / 影響範囲（本人だけか）/ 報告者を特定できるID** だけ抜く。抽出できないものは推測せず「不明」のまま保持する。

⭐ **画像は自分で直接読む。** サブエージェントに要約させない。「エラーが出ている」に潰れると手順1が始まらない。**画面に出ている文字列・イラスト・レイアウトが、そのままコードを引くためのキーになる。**

### 1. 症状の出所をコードで特定する（★このスキルの本体）

**画面に出ていたものを、コードベース上の固有名詞に変換する。** 表示文字列・アセット名・エラーコードのどれかが必ずコードのどこかにある。ここが割れると以降が全部速くなり、割れないと最後まで推測が続く。

探し方と、**関係するリポジトリの確定**（クライアントの不具合はサーバのリポジトリには無い）は `references/probes.md` の「症状の出所を探す」「関係するリポジトリの特定」。

**完了条件**: 症状を出しているコード上の名前と、その**表示条件と解除条件の両方**を言えること。解除条件を読み飛ばすと「出っぱなしになる」型の不具合を丸ごと見落とす。割れなかったら **「未特定」と明示して**手順2へ進む（以降の仮説の確度が一段下がる）。

### 2. 観測（並列・ゲート前）

**2-a. 何が使えるかを実測する。** 決め打ちしない。**エラートラッカーはプラットフォームごとに違う** — サーバは Sentry でもモバイルは Crashlytics だけ、ということが普通にある。

```bash
grep -rIl --exclude-dir={node_modules,.git,build,Pods} -E '@sentry/|SENTRY_DSN|Crashlytics|FirebaseCrashlytics|datadog|newrelic' . 2>/dev/null | head -10
```

**同時にプロジェクト側の蓄積を読む。** ダッシュボードの在り処・接続手順・指標の校正はここにしかない。コンテキストに載っている `MEMORY.md` の索引から関連項目の**本文を読む**、`CLAUDE.md` / `AGENTS.md` / `docs/` の運用記述を見る。⭐ **「未解決の宿題 / 既知の穴 / わざと放置した箇所」を明示的に探す。**

検出はヒューリスティックで網羅ではない。**ヒットしなかった基盤を「使っていない」と結論づけない。** 検出結果は手順3に1行で載せ、間違っていればユーザーに訂正してもらう。

**2-b. 観測を全部 fork で投げる。** `Agent` を `subagent_type: "fork"` で起動する（バックグラウンドで走るのでメインは待たない。コンテキストを継承するので報告内容の再提示は不要）。

| 観測 | 中身 |
|---|---|
| 実データ | エラートラッカーの実レコード。**報告者本人のイベントを特定できるか**（アカウントID・端末・アプリ版で突合）。例外の**実文字列**を持ち帰らせる |
| 規模 | **この1人の話か。** 同じエラーの総件数・影響ユーザー数・時系列。**分母**（対象プラットフォームのアクティブユーザー / 対象機能の実行回数）も取る |
| 既報 | チケット・過去の同症状・その修正 PR。**「対策済み」は何を捕まえて何を捕まえないかまで読む** |
| 対向実装 | iOS ⇔ Android、v1 ⇔ v2、web ⇔ app。**片方だけ直っていることが多く、そこが最短の答えかつ修正の設計図になる** |
| コードの反証 | 手順1で立てた筋を**反証させる**（手順4のプロンプトをそのまま使う） |

**「規模」と「既報」は必ず投げる。** 規模が無いと引き渡し先が優先度を決められない。既報が無いと、**前に塞いだつもりの穴の隣を通っているだけ**というよくある形を見逃す。

叩き方は `references/probes.md`（**必要な節だけ読む**）。全エージェントに以下を渡す。

```text
## 出力形式（この形式のみ。前置き不要）
実データ: <観測した実レコード。例外の実文字列・時刻・件数を必ず含める>
報告との一致: <端末 / OS / アプリ版 / 時刻が報告と合うか。食い違いも書く>
規模: <この1人か、広範か。実数と分母。取れないなら「分母なし」>
確からしさ: <窓・粒度・データソースを変えても同じ結論か。何をどう変えて確かめたかを書く。やっていないなら「未検証」>
取れなかったもの: <試したが取れなかったもの。なければ「なし」>
```

**`確からしさ` が「未検証」のものは仮説の根拠にしない。**

### 3. 仮説の提示（会話ゲート）

返ってきた観測を見せ、**原因クラスの仮説を具体名つきで4本まで**立てて `AskUserQuestion`（`multiSelect: true`）で選ばせる。

- **仮説を出す前に手元の観測と突き合わせる。** 既に反証できるものは提示せずに落とす
- 「クライアントのバグ」ではなく「`<ファイル:行>` の `<関数>` が `<条件>` のとき」。具体名があると人間が一目で棄却できる
- **上流（何が引き金か）と下流（なぜ復帰しないか）を分けて立てる。** 混ぜると、片方が確定しただけで全部確定したように見える
- 未到着の観測は `取得中` と明示する。**推測で内容を埋めない**

**同じ問いで「報告に書かれていない条件」も聞く**（同種の問い合わせが他に来ていないか / 直前のリリースや入稿データの変更 / 特定の機能フラグ / 心当たりなし）。CS や他メンバーしか知らない情報で、質問を1問足すだけで往復は増えない。

原因クラスの引き出しは `references/probes.md` の末尾。

### 4. 仮説の反証（並列）

選ばれた仮説ごとに `Agent` を1つ。**全部1メッセージ内で呼ぶ**（分けると直列になり並列化の意味が消える）。

```text
あなたのタスクは仮説「<仮説>」を **反証する** ことです。

## 状況
<症状 / 報告者の環境 / 影響範囲 / 手順1で特定した症状の出所>

## 既に分かっていること
<手順2の観測結果と、プロジェクト側の知見。要約せずそのまま貼る>

## 使える観測手段
<検出した基盤と、probes.md の該当節>

## 制約
- 反証できなかった場合だけ「支持」と報告する。曖昧なら「判断不能」
- **読み取り専用。** 書き込み・設定変更・チケットやコメントの投稿は一切しない
- 大きなクエリを1発で投げない。小さく刻む（タイムアウトすると全部失う）
- 取れなかったものを推測で埋めない

## 出力形式（この形式のみ。前置き不要）
判定: 支持 | 棄却 | 判断不能
根拠: <ファイル:行番号と実際のコード、または観測した実データ。数値・時刻・実文字列を必ず含める>
自己反証: <「支持」と判定したなら、その根拠が別の解釈で説明できないかを1つ以上挙げ、潰せたか書く>
取れなかったもの: <なければ「なし」>
次に見るべきもの: <支持なら次に取る観測。なければ「なし」>
```

### 5. 収束

- **支持1本** → **深掘りの前に、別軸で裏を取る。** **コードで立てた仮説は実データで、実データで立てた仮説はコードで**確かめる。エージェントは自信を持って間違える
- **支持が複数** → 因果の連鎖として構成する。**真因は最上流**。並列に並べず、支持されたノードを1つも落とさない
- **全部棄却** → 手順1に戻る。**症状の出所の特定が外れている**可能性が高い（言い換えて再投入しない）
- **判断不能が多い** → 原因ではなく**観測手段の欠落**を報告する

⭐ **確定と未確定の線を毎回引き直す。** 記録された例外の文字列は確定でも、**その手前（何が引き金か）と、その後（なぜ復帰しないか）は別の主張**で、大抵どちらも未確定のまま残る。ここを混ぜて書くと、引き渡し先が「原因は判明済み」の前提で受け取って調査が浅くなる。

途中で結論が覆ったら、その場で明示的に伝える（ユーザーが既に他所へ共有していることがある）。1〜2文で言い切って先に進む。**2周して収束しないなら結論を出さない。**

### 6. 報告

切り分けと引き渡しまで。修正の実装には進まない（求められたら別途）。

```text
## 症状
<画面に何が出たか / 直前の操作 / 報告者の環境 / 報告日時>　※不明な項目は「不明」と明記
症状の出所: <コード上の固有名詞。特定できなければ「未特定」>
検出した観測基盤: <誤っていれば訂正してもらう>

## 確定していること
<観測した実データ。例外の実文字列・時刻・件数。ここには推測を一切混ぜない>

## 確定していないこと
上流（何が引き金か）: <候補と、それぞれの根拠の強さ。特定できていないなら明記>
下流（なぜ復帰しないか）: <同上>

## 規模
<実数 / 影響ユーザー数 / 分母に対する比率 / 慢性か新規か>
※ **到達ユーザー率と1回あたりの失敗率は別の指標。混ぜると「レアな不具合」と誤読される**

## 棄却したもの
<仮説> — <棄却の根拠>

## 既報との関係
<過去の同症状のチケット。前の修正が何を捕まえ、何を捕まえていないか>

## 回避策
<ユーザーに案内できるもの。無ければ「なし」>

## 観測できなかったもの
<取れなかった観測と、その理由>

## 引き渡し先と、次に取るべき手
<どのチームの担当か / 最も情報利得の大きい観測 or 修正の当たり>
```

**棄却したものと、確定していないことを必ず載せる。** この2つが、引き渡し先が最初に知りたい情報。

確度「高」は**実ログの一致・IDの一致など、観測データによる直接の裏付けがある場合だけ**。コードを読んで筋が通ることは根拠にならない（**通る筋は複数ある**）。消去法は「中」以下。
