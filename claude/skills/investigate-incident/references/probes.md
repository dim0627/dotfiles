# 観測手段リファレンス

**必要になった節だけ読む。**

## 共通原則

- **名前を決め打ちしない。** 環境名・プロジェクト名・リソース名は必ず一覧を取得して実在する値から選ぶ。決め打ちの最悪の壊れ方は、クエリが0件を返して**障害中のシステムを「異常なし」と報告する**こと
- **取れなかったものは「取得失敗」と書く。** 観測の欠落自体が報告すべき情報
- **絶対値より形状。** 「エラー200件」より「10分前から階段状に増え継続中」の方が原因クラスを絞る。バケットが2〜3点では形状は出ない。**最低5〜6点**取り、取れないなら「形状は不明」と書く

## 変更タイムライン

```bash
git log --format='%h %ad %an %s' --date=iso -30
git log --format='%h %ad %s' --date=iso --since='<発生時刻の3時間前>'
```

**デプロイ時刻はコミット時刻と別物**（マージから反映までのラグ、手動デプロイ、ロールバック）。コミット履歴だけで「デプロイ相関なし」と結論づけない。実デプロイ時刻は各プラットフォームの節で取る。

コード以外（環境変数 / フラグ / 外部SaaSの設定 / DNS / 証明書 / 依存先のメンテ）はリポジトリから見えないのでユーザーに聞く。

## 人の操作（誰がいつ何をしたか）

停止・復旧・設定変更の裏には人がいることが多く、**監視ログ側には人為の痕跡が残らない**。引かないと「自然に起きた障害」として読んでしまう。

取るもの: **操作者 / 操作名 / 対象リソース / 時刻**。最低でもデプロイ・ロールバック履歴（各プラットフォームの節）、可能ならクラウド側の監査ログ。

- **「記録されていない」を「操作が無かった」と読まない。** 読み取り系や一部のデータ操作は既定で監査対象外のことが多く、有効化して初めて記録される。取れなかったなら「記録対象外の可能性」として報告する
- **保持期間で窓の外に落ちる。** 数日前から続いている障害では既定の保持期間を超えていることがある
- **操作者がサービスアカウント名義で出る。** 人に紐付かないのを「人為ではない」と読まない。CI・オートスケーラ・スケジューラの操作と人の手動操作が同じログに混ざる。**逆に人の名義でもスクリプト実行のことがある**
- **正常系の運用操作が大量に混ざる。** 障害時刻の窓に絞ってから対象リソースで引く

CLI・ログ名・フィルタ構文はプラットフォームごとに違う。**うろ覚えで打たない** — `--help` で確認するか、手順1-a で探したプロジェクト側の知見を見る。

## Sentry

MCP: `mcp__sentry__*`（未認証なら `/mcp` で認証してもらう）

**1. 組織とプロジェクト** — `find_organizations()` → `find_projects(organizationSlug)`。**リポジトリ名と一致しない前提で探す**（monorepo なら1リポジトリが web / api など複数プロジェクトに跨る）。ビルドプラグイン設定に平文で入っていることが多い:

```bash
grep -rnE --exclude-dir={node_modules,.git,dist,.next} '(org|project)[[:space:]]*:[[:space:]]*["'"'"']' . | grep -iE 'sentry|org:|project:'
```

絞れないなら聞く。**決め打ちすると、見落としたプロジェクトの障害が「異常なし」になる。**

**2. 環境名** — `environment:production` は決め打ちできない（実測例: `production` / `vercel-production` / `prd` / `prod`）。実際に届いている値を取る:

```text
search_events(organizationSlug=<org>, projectSlug=<project>, dataset='errors',
  fields=['environment','count()'], sort='-count()', period='24h', limit=20)
```

**3. 内訳** — `fields=['error.type','count()']` で同様に取る。**`24h` と `1h` の2通りで取り差分を見る。** 24h に出ず 1h に出る型が今まさに燃えているもの。「元から出ていたエラー」と「今回新しく出たエラー」の区別が決定的。

**4. 形状** — **上の期間集計では形状は出ない。** `count()` は期間の合計なので、1時間100件がスパイク1発でも定常発生でも同じ数字になる。

1. **MCP のスキーマを確認する。** 時系列を返す仕組みがある（events-timeseries 系は `yAxis` に集計関数を指定しバケット単位で返す）。**パラメータ名をうろ覚えで打たない**
2. 取れないなら period を刻んで累積で取り（`1h` / `3h` / `6h` / `12h` / `24h`）、隣接期間の差でバケットを自作する

読み方: 急峻 → 直前の変更・依存先の停止 / 階段 → 段階的ロールアウト・順次障害 / じわじわ → 枯渇・リーク / 周期 → バッチ・cron・トラフィックパターン

**5. 個別 issue** — `get_sentry_resource` で開く。**真因は表層メッセージの下に chain されている**ことが多い（`During handling of the above exception, another exception occurred` の下）。ミニファイ時（`index.js:100:36977`）は行番号が使えないので `culprit` / `transaction` とメッセージ内の具体文字列で `Grep` する。自力で無理な場合だけ `analyze_issue_with_seer`（数分かかるので無条件のフォールバックにしない）。

## Cloudflare Workers

MCP: `mcp__cf-observability__*`（ログ・メトリクス）、`mcp__cf-builds__*`（ビルド）。**パラメータは呼ぶ前にスキーマを確認する。**

- **Worker の特定** — `workers_list` と `wrangler.jsonc` / `wrangler.toml` の `name` を突合する
- **ログ** — `query_worker_observability`。フィールド名が不明なら先に `observability_keys` / `observability_values` でキーと値の候補を取る。**推測して0件を「異常なし」と読まない**
- **デプロイ相関** — `workers_builds_list_builds(workerId=<workers_list で得たID>)`。**Workers Builds は GitHub/GitLab 連携の CI/CD。`wrangler deploy` を手元や別CIから打つと履歴に出ない。** 空を「デプロイなし」と読まず「この経路では追えない」と報告する
- **バインディング先** — 障害は本体でなくバインディング先（D1 / KV / R2 / Durable Objects / 外部fetch）のことが多い。`wrangler.jsonc` の定義を読み、どのバインディング経由でエラーが出ているかをログから特定する

## Vercel

**フラグをうろ覚えで打たない。`vercel <subcommand> --help` で確認する**（バージョンで変わる）。

```bash
vercel ls          # デプロイ一覧＝デプロイ時刻の取得元
vercel inspect <deployment-url>
vercel logs <deployment-url>
```

未ログイン・未リンクなら止まる。`! vercel login` をユーザーに打ってもらう（対話ログインは自分で完了できない）。**Production への promote は build 時刻と別**なので、promote 時刻の方を症状開始と突き合わせる。

## Slack

価値はアラート本文そのものより **「他に誰が何に気づいているか」** と **「通知の時系列」**:

- 同時刻に別チャンネルで別のアラート → 影響範囲が想定より広い証拠
- 外部SaaSからのステータス通知 → 自分のコードは無実の証拠
- アラートの**発火間隔**（連続 / 単発 / 収束したか）

**書き込みは絶対に自動でしない。** 障害対応中の誤投稿は影響が大きい。文面はドラフト提示までに留め、投稿はユーザー本人が行う。

## 外部要因（DNS / 証明書 / CDN / プラットフォーム）

**アプリのログに何も残らないタイプの障害はここを疑う。**

```bash
dig <domain> +short
curl -sS -o /dev/null -w 'http=%{http_code} dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} total=%{time_total}\n' https://<domain>/
curl -sSI https://<domain>/ | head -20
echo | openssl s_client -connect <domain>:443 -servername <domain> 2>/dev/null | openssl x509 -noout -dates
```

`time_namelookup` だけ長い → DNS / `time_appconnect` で失敗 → 証明書・TLS / CDN のエラーヘッダ → プラットフォーム / 全部速いのに 5xx → アプリまで到達しており外部要因は薄い。

**1回の curl で確定しない。** 自分の回線・DNSキャッシュ・実行地点の影響を強く受け、単発の結果は自分の環境の問題と区別できない。**独立した観測を最低2つ**組み合わせる（時間をおいて再現するか / 同じCDN上の健全な別ドメイン / 別ネットワーク・別リゾルバ `dig @8.8.8.8` / サーバ側にリクエストが到達しているか）。1つも取れないなら「判断不能」。

**ステータスページが「All Systems Operational」でも障害を否定しない**（更新は常に遅れる）。

`Load failed` / `Network error` / タイムアウトは**ホストが自分の管理下かで意味が正反対**になる: 外部ホスト・散発 → ユーザー側のネットワーク断で障害ではない / **自ドメイン（外部SaaSを自ドメインのCNAMEで配信する場合を含む）・継続中 → CNAME・証明書・CDN の障害。最優先で追う**。

## リソース枯渇

「じわじわ悪化して閾値で崩れる」「再起動で一時回復する」症状はこれ。**単発の値でなく傾きを見る**（増え続けているか、頭打ちか）。

観測対象: DB接続数 / メモリ使用量 / レート制限のヘッダ（`X-RateLimit-*`、`Retry-After`）/ プラットフォームのクォータ（サブリクエスト数、CPU時間、実行時間）

**必ず上限値とセットで取る。** 使用量だけでは枯渇か判定できない。上限が取れないなら「判断不能」と報告する。

### 消費の内訳（誰が食っているか）

上位数件で全体の大半を占めるのが普通なので、内訳が取れれば原因クラスの推測を経由せずに核心へ届く。**並べ方の一般形は「対象別の仕事量 ÷ 実行回数」。**

- ✅ 仕事量: 読んだブロック数 / スキャン行数 / 処理バイト数 / アロケーション回数 / CPU時間
- ❌ 結果: レイテンシ / 応答時間 / 平均実行時間

**結果の指標で並べない。** 負荷が上がると、仕事量が変わっていない処理まで一様に遅く見える。それは飽和の**結果**なので、上位に並ぶのは犯人でなく巻き添えになる。**総量で並べるのも同じくダメ**（単に呼ばれた回数が多いものが来る）。**1回あたりの仕事量が増えているものだけが本当に劣化している。**

**平常時の同じ内訳（前日の同時刻・障害前の窓）と並べる。** 単独のランキングは「元から重い」と「今回重くなった」を区別できない。

**具体的な取得手段（接続方法・ダッシュボード・テーブル名・データソースID）はプロジェクト側に蓄積されていることが多い。** 汎用の手順を組む前に、手順1-a で探した知見を見る。

## 原因クラスの引き出し

| クラス | 典型症状 | 決定的な観測 |
|---|---|---|
| 直前の変更（デプロイ・設定・フラグ） | 特定時刻から急峻に立ち上がる | 変更時刻と症状開始の一致 |
| 依存先の障害（DB / 外部API / SaaS） | 依存先を使う経路だけ死ぬ。他は健全 | 依存先のステータス、エラーの発生元 |
| リソース枯渇 | じわじわ悪化して閾値で崩れる。再起動で一時回復 | 使用量の時系列と上限値 |
| データ起因 | 全体は健全、特定リクエストだけ失敗。再現性が入力依存 | 失敗リクエストの入力の共通点 |
| 負荷・トラフィック変動 | 流量の増加と同期。特定時間帯に集中 | リクエスト数と症状の相関 |
| 外部要因（DNS / 証明書 / CDN） | 経路全体が死ぬ。アプリのログに何も残らない | 自ドメインか外部かの切り分け |

**「アプリのログに何も残っていない」を「異常なし」と読まない。** ただし単独で結論の根拠にもしない。ログの不在は「リクエストがアプリに到達していない」の**候補**であって証拠ではなく、ログ基盤の停止・取り込み遅延・サンプリング・ログレベルの設定漏れでも同じ見え方になる。**独立した観測を組み合わせて確定する**（エッジ側にリクエストが到達しているか / ログ基盤が他サービスのログを受けているか / 別クライアント・別リージョンで同じ症状が出るか）。1つも取れないなら「判断不能」。
