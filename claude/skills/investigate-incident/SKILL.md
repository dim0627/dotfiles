**今起きている（か直前に起きた）障害の初動調査。** 原因クラスの切り分けと根拠の提示まで。修正とポストモーテムは含まない。

## 原則

**この形である理由**

1. **観測は人間の選択を待たない。** 観測面は固定（変更 / ログ / リソース / エラートラッカー / 人の操作）なので、聞くまでもなく全部並列で投げる。ユーザーが選んでいる時間を観測時間に変えるのが初動速度の正体
2. **エージェントは反証者。** 「支持する証拠を探せ」ではなく「**反証しろ。できなかった場合だけ支持と報告しろ**」。偽陽性（無関係な異常値を犯人に仕立てる）が最も高くつく
3. **返り値は契約で固定する。** 生の数字を持ち帰らせない。統合がメインに乗ると会話が止まる

**そのまま信じないもの**（以降この3語をこの意味で使う）

- **証拠の不在** — 不在の証拠ではない。0件もログの不在も「取れなかった」であって「無かった」ではない
- **アーティファクト** — 欠落や異常値に見えるものの多くは、取得窓・集計単位・ログの欠落率が作る。**窓と粒度を変えても同じ結論になるか**で切り分ける
- **人為** — 停止・復旧・設定変更の裏には人がいる。監視ログ側からは自然発生と区別できないので、確かめずにメカニズムとして読むと丸ごと外す

## 手順

### 0. 入力の読み取り（コードは読まない）

貼られたものから **症状 / 発生時刻とその性質（突然・じわじわ・周期的）/ 影響範囲 / 観測元 / 現在も継続中か** だけ抜く。

抽出できないものは推測せず「不明」のまま保持する（特に発生時刻を埋めると後段のデプロイ相関が全部無意味になる）。画像は自分で直接読む — 要約させるとグラフの形状という一番効く情報が落ちる。

### 1. 観測（並列・ゲート前）

**1-a. 何が使えるかを実測する。** 決め打ちしない。monorepo ではルート直下にない。

```bash
find . -maxdepth 3 \( -name node_modules -o -name .git -o -name .next -o -name dist \) -prune -o \
  -type f \( -name 'wrangler.json*' -o -name 'wrangler.toml' -o -name 'vercel.json' -o -name 'fly.toml' \) -print 2>/dev/null
grep -rl --exclude-dir={node_modules,.git,.next,dist} -E '@sentry/|SENTRY_DSN|datadog|newrelic|@opentelemetry' . 2>/dev/null | head -10
```

**同時にプロジェクト側の蓄積を読む。** ダッシュボードの在り処・接続手順・指標の校正（「このアラートは実影響より大きく出る」）は、汎用のリファレンスには原理的に書けない。ここにしかない。

- コンテキストに載っている `MEMORY.md` の索引を見て、関連しそうな項目の**本文を読む**（索引は載るが本文は読みに行かないと出てこない）
- `CLAUDE.md` / `docs/` の運用・監視の記述
- ⭐ **「未解決の宿題 / 既知の穴 / 検知できていないもの」を明示的に探す。** 同じ症状の再来か、**前回わざと放置した穴に落ちた**ケースが多い。「対策済み」も**何を捕まえて何を捕まえないか**まで読む — 前回作ったアラートが今回の失敗モードには構造的に鳴らない、はよくある

**優先するが鵜呑みにしない。** 記録時点の情報なので、リソース名・権限・エンドポイントの実在は現物で確認する。

検出はヒューリスティックで網羅ではない（SDKの表記揺れ、CI側だけの設定、リポジトリ外の監視は拾えない）。**ヒットしなかった基盤を「使っていない」と結論づけない。** 検出結果は手順2に1行で載せ、間違っていればユーザーに訂正してもらう。

**1-b. 観測を全部 fork で投げる。** `Agent` を `subagent_type: "fork"` で起動する（バックグラウンドで走るのでメインは待たない。コンテキストを継承するのでアラート内容の再提示は不要）。

| 観測 | 中身 |
|---|---|
| 変更 | 発生時刻前後のコミット・デプロイ・設定変更 |
| ログ | アプリ / インフラのログ。形状と、どのエラー型が出ているか。**あわせて「今も継続中か / いつ復旧したか」を確定させる**（継続中と復旧済みでは次の手が全く違う。火を消す vs 事後の切り分け） |
| リソース | インスタンス・DBのメトリクス。上限との距離。**飽和していたら消費の内訳まで掘る** |
| エラートラッカー | Sentry 等。**1-a で検出できた場合のみ** |
| 人の操作 | **誰がいつ何をしたか。** デプロイ / ロールバック履歴、監査ログ、手動オペの記録 |

**「人の操作」は必ず投げる。** ユーザーは自分がやったことしか知らず、他のメンバーや自動化の操作は履歴を引かないと出てこない。

発生時刻が不明なら「直近24h」で投げ、判明した時点で絞る。叩き方は `references/probes.md`（**必要な節だけ読む**）。全エージェントに以下を渡す。

```text
## 出力形式（この形式のみ。前置き不要）
形状: <いつ・どう変化したか。急峻 / 階段 / 周期 / じわじわ。判定できないなら「不明」>
内訳: <何が上位を占めているか。実数値つき>
平常時との差: <比較窓と、その差>
確からしさ: <窓・粒度・ログ種を変えても同じ結論か。何をどう変えて確かめたかを書く。やっていないなら「未検証」>
取れなかったもの: <試したが取れなかったもの。なければ「なし」>
```

**`確からしさ` が「未検証」のものは仮説の根拠にしない。** アーティファクトのまま会話に定着する。

### 2. 仮説の提示（会話ゲート）

返ってきた観測を見せ、**原因クラスの仮説を具体名つきで4本まで**立てて `AskUserQuestion`（`multiSelect: true`）で選ばせる。

- **仮説を出す前に手元の観測と突き合わせる。** 既に反証できるものは提示せずに落とす。自分で取ったデータに否定される仮説を出すと、会話がそこに引きずられる
- 「デプロイ起因」ではなく「30分前の <コミット名>」。具体名があると人間が一目で棄却できる
- 各仮説に「これを流すと何が分かるか」を1行添える
- 未到着の観測は `取得中` と明示する。**推測で内容を埋めない**（無関係なコミットが犯人として会話に定着する）
- ⏱ **「これが返れば仮説空間が半分に割れる」と言える観測が1本あるなら、それが返るまでゲートに行かない。** 上限は「他の観測が全部返るまで」 — そこまでで返らないならゲートを開け `取得中` として出す（壁時計で判断しない。何分かかるかは環境で変わる）。決定打が特定できていない／複数あるなら待たない
- **ゲートは往復1回ぶんのユーザーの注意を使う。** 手順4で全部棄却なら2回目を開くが、初動で外した選択肢に1回使い切ると2回目のコストが上がる

**同じ問いで「リポジトリの外で直前に変わったもの」も聞く**（環境変数 / フィーチャーフラグ / 外部SaaSの設定 / DNS・証明書 / 依存先の計画メンテ / 手動オペ / 心当たりなし）。リポジトリからは原理的に見えないのに情報価値が高く、質問を1問足すだけなので往復は増えない。

原因クラスの引き出しは `references/probes.md` の末尾。

### 3. 仮説の反証（並列）

選ばれた仮説ごとに `Agent` を1つ。**全部1メッセージ内で呼ぶ**（分けると直列になり並列化の意味が消える）。

```text
あなたのタスクは仮説「<仮説>」を **反証する** ことです。

## 状況
<症状 / 発生時刻 / 影響範囲 / 観測元>

## 既に分かっていること
<手順1の観測結果と、プロジェクト側の知見。要約せずそのまま貼る>

## 使える観測手段
<検出した基盤と、probes.md の該当節>

## 制約
- 反証できなかった場合だけ「支持」と報告する。曖昧なら「判断不能」
- **読み取り専用。** 書き込み・設定変更・スケール操作・統計のリセットは一切しない
- 大きなクエリを1発で投げない。小さく刻む（タイムアウトすると全部失う）
- 認証情報はファイルに書かない、標準出力に出さない
- 取れなかったものを推測で埋めない。コードは修正しない

## 出力形式（この形式のみ。前置き不要）
判定: 支持 | 棄却 | 判断不能
根拠: <観測した実データ。数値・時刻・ログの実文字列を必ず含める>
自己反証: <「支持」と判定したなら、その根拠が別の解釈で説明できないかを1つ以上挙げ、潰せたか書く。取得窓・集計単位を変えても成立するか。人為操作で説明できないか>
取れなかったもの: <なければ「なし」>
次に見るべきもの: <支持なら次に取る観測。なければ「なし」>
```

### 4. 収束

- **支持1本** → **深掘りの前に、別軸の観測で裏を取る。** エージェントは自信を持って間違える（「最有力」と言い切って返してくる）。同じ軸で厚くしても間違いは厚くなるだけなので、**コードで立てた仮説は実データで、ログで立てた仮説は別ソースで**確かめる。裏が取れてから「次に見るべきもの」へ進む
- **支持が複数** → 因果の連鎖として構成する（デプロイ → 接続リーク → 枯渇）。**真因は最上流**。並列に並べず、支持されたノードを1つも落とさない。最有力だけ残すと下流だけ対処して再発する
- **全部棄却** → 切り口が外れている。手順2に戻り**別の軸で**立て直す（時間軸を広げる / 影響範囲の前提を疑う / そもそも障害かを疑う）。言い換えて再投入しない
- **判断不能が多い** → 原因ではなく**観測手段の欠落**を報告する

途中で外から情報が入ったら遠慮なく仮説を組み替えてよい（**外部の情報で自分の仮説が棄却されるのは正しく機能している状態**）。ただし他人が持ってきた数値も鵜呑みにしない — 帰属やベースラインの取り方が誤っていることがある。自分の観測で裏を取り、食い違ったら食い違いごと報告する。

**途中で出した結論が覆ったら、その場で明示的に伝える。** 調査中の仮説はユーザーが他所に共有していることがあり、黙って差し替えると誤情報が独り歩きする。「あの筋は消えた、根拠はこれ」と1〜2文で言い切って先に進む — 長い自己批判は要らない。

**2周して収束しないなら結論を出さない。** 「ここまで分かった / ここが観測できていない」で返す。根拠の薄い犯人を確定させて対策を打ち、実際の原因が生き残るのが最悪。

### 5. 報告

切り分けまで。修正の実装やポストモーテムには進まない（求められたら別途）。

```text
## 状況
<症状 / 発生時刻 / 影響範囲 / 継続中か（復旧済みなら復旧時刻と、自然復旧か人の操作か）>　※不明な項目は「不明」と明記
検出した観測基盤: <誤っていれば訂正してもらう>

## 最有力: <原因クラス>
根拠: <観測した実データ。数値・時刻・ログの実文字列>
確度: 高 / 中 / 低 ＋ そう言える理由

## 支持された因果連鎖（支持が2本以上なら必ず）
<上流> → <中流> → <観測された症状>
各ノードに根拠となる実データ。真因は最上流 — 下流だけ対処しても再発する

## 棄却したもの
<仮説> — <棄却の根拠>

## 観測できなかったもの
<取れなかった観測と、その理由>

## 次に取るべき手
<最も情報利得の大きい観測 or 応急処置>
```

**棄却したものを必ず載せる。** 「何を見なくてよくなったか」は障害対応中に最も価値が高い。

確度「高」は**時刻の一致や実ログの一致など、観測データによる直接の裏付けがある場合だけ**。消去法は「中」以下。**単一のログ種・単一の取得窓しか根拠が無いものは「高」にしない**（アーティファクトと区別できていない）。
