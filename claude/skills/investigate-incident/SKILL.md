**今まさに起きている（か、直前に起きた）障害の初動調査**をする。目的は原因クラスの切り分けと根拠の提示までで、コードの修正やポストモーテムの執筆はここには含めない。

このスキルが解いている問題は「並列に投げること」ではなく **「何を観測すべきかの選定」** と **「ユーザーが選んでいる間に待ち時間を作らないこと」** の2つ。

## 設計の前提（守らないと意味がなくなる）

1. **観測は仮説単位で分割する。メトリクス種別で分割しない。**
   「Sentry担当」「DB担当」のように切ると、各エージェントが数字を持ち帰るだけで統合判断が全部メインに乗り、ユーザーとの会話が止まる。「デプロイ起因である」「依存先の障害である」のように**仮説を1エージェントに1つ**割り当て、判定まで持たせる。

2. **仮説エージェントには棄却を試みさせる。** 「この仮説を支持する証拠を探せ」ではなく「**この仮説を棄却しろ。棄却できなかった場合だけ支持と報告しろ**」と指示する。障害調査では偽陽性（無関係な異常値を犯人に仕立てる）が最も高くつく。

3. **無条件観測は会話の前に投機的に起動する。** ユーザーに何を聞くまでもなく必ず要る観測（手順1参照）は、仮説を提示する前にバックグラウンドで走らせる。ユーザーが選択している時間を観測時間に変換するのがこのスキルの初動速度の正体。

## 手順

### 0. 入力の読み取り（コードは読まない）

ユーザーが貼ってきたもの（スクリーンショット / エラーメッセージ / スタックトレース / 障害報告の文章）から、以下だけを抽出する。**ここでコードベースを読み始めてはいけない。** 初動が数十秒遅れ、並列化の利得が消える。

- **症状** — 何が壊れているか（5xx / タイムアウト / データ不整合 / 特定機能だけ死んでいる 等）
- **発生時刻とその性質** — いつから。突然か、じわじわか、周期的か
- **影響範囲の手掛かり** — 全体か一部エンドポイントか、特定ユーザーだけか
- **観測元** — その情報がどこから来たか（Sentry / Slack通知 / ユーザー報告 / 自分で気づいた）

画像が貼られている場合は自分で直接読む。要約させるとグラフの形状（急峻な立ち上がりか階段状か）という一番効く情報が落ちる。

抽出できない項目は**推測で埋めず「不明」として保持する**。特に発生時刻が不明なまま進めると、後段のデプロイ相関がすべて無意味になる。不明なら手順2の質問に含める。

### 1. 観測基盤の検出と無条件観測の起動（並行・自動）

**この2つは同じターンで同時に実行する。**

**1-a. どの観測基盤が対象かをリポジトリから実測する**

決め打ちしない。**ルート直下だけを見ない**（monorepo では `apps/*/wrangler.jsonc` のように1〜2段下にある）。1回の Bash で判定する。

```bash
find . -maxdepth 3 \( -name node_modules -o -name .git -o -name .next -o -name dist \) -prune -o \
  -type f \( -name 'wrangler.json*' -o -name 'wrangler.toml' -o -name 'vercel.json' -o -name 'fly.toml' \) -print 2>/dev/null
grep -rl --exclude-dir={node_modules,.git,.next,dist} -E '@sentry/|SENTRY_DSN|datadog|newrelic|opentelemetry|@opentelemetry' . 2>/dev/null | head -10
git log --oneline -20
```

詳しい叩き方は `references/probes.md` を読む（**必要になった基盤の節だけ読む**）。

**この検出はヒューリスティックであり、網羅ではない。** SDK の表記揺れ、CI 側だけで設定されている基盤、リポジトリ外の監視（アップタイム監視・APM の SaaS 側設定）は原理的に拾えない。したがって:

- **ヒットしなかった基盤を「使っていない」と結論づけない。** 静かにスキップすると、実際に燃えている基盤を見ないまま「異常なし」を報告することになる。これがこのスキルの最悪の壊れ方
- **検出結果は手順2の提示に必ず含める**（「検出した基盤: Cloudflare Workers / Sentry」の1行）。間違っていればユーザーが即座に訂正できる。会話の往復は増えない
- 検出が空振りした場合は「検出失敗」として提示し、対象基盤をユーザーに確認する。ただし調査自体は止めない

リポジトリの外側で起きている障害（外部SaaSの障害、DNS、決済プロバイダ等）の可能性がある場合、リポジトリに手掛かりがないのは正常。

**1-b. 無条件観測をバックグラウンドで起動する**

`Agent` を `subagent_type: "fork"` で起動する。fork はバックグラウンドで走り、完了時に通知が返るので、**メインは待たずに手順2へ進める**。fork は現在のコンテキストを継承するので、貼られたアラート内容を改めて渡す必要はない。

無条件で起動するのは以下。どんなインシデントでも必ず効き、ユーザーに聞く必要がないものだけに限る（多すぎると初動が重くなる）。

| 観測 | 内容 | なぜ無条件か |
|---|---|---|
| 変更タイムライン | 発生時刻前後のコミット・デプロイ・設定変更 | 障害原因の最大クラスが「直前の変更」。相関の有無は必ず問われる |
| 症状の時系列 | エラー率・レイテンシが「いつ・どう」変化したか（絶対数でなく形状） | 立ち上がりの形（急峻/階段/周期）が原因クラスを大きく絞る |

発生時刻が不明の場合、変更タイムラインは「直近24hのデプロイ」として起動し、時刻が判明した時点で絞り込む。

**この2つはメインコンテキストで直接やらない。** 手順2の提示が遅れる。

### 2. 仮説の展開とユーザーによる選択（唯一の会話ゲート）

症状から**原因クラスの仮説を4〜6本**立て、`AskUserQuestion`（`multiSelect: true`）で「どれを流すか」を提示する。ユーザーは選ぶだけで済む形にする。

仮説の出発点として以下の原因クラスを検討する。**症状に対して具体化してから提示する**（「デプロイ起因」ではなく「30分前の <コミット名> で入った変更が原因」のように、リポジトリから取れた具体名を入れる。具体名があると人間が一目で棄却でき、選択が速くなる）。

| 原因クラス | 典型的な症状 | 決定的な観測 |
|---|---|---|
| 直前の変更（デプロイ・設定・フラグ） | 特定時刻から急峻に立ち上がる | 変更時刻と症状開始の一致 |
| 依存先の障害（DB / 外部API / SaaS） | 依存先を使う経路だけ死ぬ。他は健全 | 依存先のステータス・エラーの発生元 |
| リソース枯渇（接続数 / メモリ / レート制限 / クォータ） | じわじわ悪化して閾値で崩れる。再起動で一時回復 | 使用量の時系列と上限値 |
| データ起因（特定レコード・想定外の入力） | 全体は健全、特定リクエストだけ失敗。再現性が入力依存 | 失敗リクエストの入力の共通点 |
| 負荷・トラフィック変動 | 流量の増加と同期。特定時間帯に集中 | リクエスト数と症状の相関 |
| 外部要因（DNS / 証明書 / CDN / プラットフォーム障害） | 経路全体が死ぬ。アプリのログに何も残らない | 自ドメインか外部かの切り分け、プロバイダのステータス |

**「アプリのログに何も残っていない」を「異常なし」と読まない。** ただしこれを単独で結論の根拠にもしない。ログの不在は「リクエストがアプリに到達していない（＝外部要因・経路障害）」を示す**候補**であって証拠ではなく、以下でも同じ見え方になる:

- ログ基盤自体が停止している / 取り込みが遅延している
- サンプリング設定で落とされている
- ログレベル・フィルタの設定漏れ（そもそも出力されていない）

**確定するには独立した観測を組み合わせる**（エッジ側のログにリクエストが到達しているか、ログ基盤自体が他のサービスのログを受けているか、別クライアント・別リージョンから同じ症状が出るか）。1つも取れないなら「判断不能」にする。

提示の際は**各仮説の脇に「これを流すと何が分かるか」を1行**添える。選択の判断材料になる。

**同じ問いの中で「リポジトリの外で直前に変わったもの」も1問だけ聞く**（`multiSelect`）。環境変数 / フィーチャーフラグ / 外部SaaSの設定 / DNS・証明書 / 依存先の計画メンテ / 心当たりなし。これらはリポジトリからは原理的に見えないのに情報価値が非常に高い。**質問を1問足すだけなので会話の往復は増えない**（手順0で判明していれば省く）。

ユーザーが「全部」と言ったらそのまま全部流してよい。仮説は最大6本までに抑える（それ以上は仮説の粒度が細かすぎるサイン。原因クラスのレベルまで戻して括り直す）。

### 3. 並列調査

選ばれた仮説ごとに `Agent` を1つ起動する。**全エージェントを1メッセージ内で同時に呼ぶ**（別メッセージに分けると直列になり、並列化の意味が消える）。

エージェントへの指示には必ず以下を含める。

```text
あなたのタスクは仮説「<仮説>」を **棄却する** ことです。

## 状況
<症状 / 発生時刻 / 影響範囲 / 観測元>

## 使える観測手段
<手順1-aで検出した基盤と、references/probes.md の該当節の内容>

## 制約
- 棄却できなかった場合だけ「支持」と報告すること。曖昧なら「判断不能」を選ぶ
- 観測できなかったものを推測で埋めない。取れなかったなら「取得失敗」と書く
- コードの修正はしない。調査のみ

## 出力形式（この形式のみ。前置き不要）
判定: 支持 | 棄却 | 判断不能
根拠: <観測した実データ。数値・時刻・ログの実文字列を必ず含める>
観測できなかったもの: <試したが取れなかったもの。なければ「なし」>
次に見るべきもの: <この仮説が支持なら次に取るべき観測。なければ「なし」>
```

**判定・根拠・次の3点セットを出力契約として固定する**のが要点。これがないと各エージェントが自由形式の長文を返し、統合がメインの負荷になって会話が止まる。

エージェントの待ち時間中、メインは**手順1-bの無条件観測のうち、実際に結果が返ってきたものだけ**をユーザーに見せて会話する。

**「もう返ってきているはず」と仮定しない。** 未到着のものは `取得中` と明示し、**推測で内容を埋めない**。変更タイムラインを推測で語ると、実際には無関係なコミットが犯人として会話に定着し、以降の調査全体が引きずられる。到着した時点で初めて内容に言及する。

### 4. 収束

全エージェントの判定を集計する。

- **支持が1本** → その仮説を深掘りする。「次に見るべきもの」に沿って追加調査し、根拠を厚くする
- **支持が複数** → 因果の順序を考える（例：デプロイ → 接続リーク → リソース枯渇。真因は最上流のデプロイ）。並列に並べず**連鎖として構成し、支持されたノードを1つも落とさずに手順5の「🔗 支持された因果連鎖」へ書く**。最有力を1つ選んだ時点で他の支持仮説を捨てると、下流だけ対処して再発させることになる
- **全部棄却** → 仮説の立て方が外れている。手順2に戻り、**別の切り口で**仮説を立て直す（時間軸を広げる／影響範囲の前提を疑う／「そもそも本当に障害か」を疑う）。同じ仮説を言い換えて再投入しない
- **判断不能が多い** → 観測できていない。原因ではなく**観測手段の欠落**を報告する（それ自体が改善提案になる）

**2周しても収束しない場合、無理に結論を出さない。** 「ここまで分かった／ここが観測できていない」を報告してユーザーに返す。障害調査で最悪なのは、根拠の薄い犯人を確定させて対策を打ち、実際には別の原因が生き残ることなので。

### 5. 報告

切り分け結果までを報告する。修正の実装やポストモーテムの執筆には進まない（求められたら別途）。

```text
## 状況
<症状 / 発生時刻 / 影響範囲> ※不明な項目は「不明」と明記
検出した観測基盤: <手順1-aの結果。誤っていれば訂正してもらう>

## 切り分け結果

### 🎯 最有力: <原因クラス>
- **根拠**: <観測した実データ。数値・時刻・ログの実文字列>
- **確度**: 高 / 中 / 低 ＋ そう言える理由

### 🔗 支持された因果連鎖（支持が2本以上あった場合は必ずこの形で書く）
<上流> → <中流> → <観測された症状>
- **<上流のノード>**: <根拠となる実データ>
- **<中流のノード>**: <根拠となる実データ>
- **真因と見なすノード**: <最上流のノード> — 下流だけ対処しても再発する

### ❌ 棄却したもの
- <仮説> — <棄却の根拠>（1行ずつ。何を見なくてよくなったかを示す）

### ❓ 観測できなかったもの
- <取れなかった観測と、その理由>

## 次に取るべき手
1. <最も情報利得の大きい観測 or 応急処置>
```

**棄却した仮説を必ず載せる。** 「何を見なくてよくなったか」は障害対応中に最も価値が高い情報で、これがないと同じ場所を何度も調べることになる。

確度を「高」にしてよいのは、**時刻の一致や実ログの一致など、観測データによる直接の裏付けがある場合だけ**。「他が全部棄却されたから消去法で」は確度「中」以下にする。
