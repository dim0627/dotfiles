# review-loop（反復レビュー）

ローカルの変更に `review-code` を当て、指摘を直し、また当てる。これを**新しい指摘が枯れるまで**繰り返す。

引数があれば仕様ソース（issue / PRD の URL やパス）として扱う。**レビュー対象は常にローカルの変更**であって、渡された URL ではない。URL は「コードがこの要求を満たしているか」を照合する基準として使う。

## なぜ回すのか

1周では終わらない。**修正そのものが新しい欠陥を持ち込む**からで、しかも持ち込まれるのは直前の指摘と同じ種類のものになりやすい。「この値は定数だ」と指摘されて別のフィールドに差し替え、それもまた定数だった、という形で繰り返す。

直す側は前の周の文脈を持ち続けるので、自分の思い込みには気づけない。**次の周のまっさらなレビュアーがそれを拾う。** これがこのループの本体で、周を重ねること自体が目的ではない。

## 入口ゲート

リポジトリの静的チェック（lint / 型検査 / テスト）を実行し、**緑になってから**ループに入る。赤のまま回さない。

ゲートは**入口であって停止条件ではない**。ここを取り違えると、緑になった時点で「終わった」ことになってループが1周も走らない。狙っているのは緑の先に残っている欠陥なので、緑はスタート地点になる。

コマンドはリポジトリの `package.json` / `Makefile` / `CLAUDE.md` から読む。

## 手順

### 1. スコープを凍結する

- 対象の差分を確定する（作業ツリー、または指定された固定点からの差分）
- レビュー対象外のパスを決める（`docs/` など、コードでないもの）
- 仕様ソースを取得する。引数で渡されていればそれを、無ければコミットメッセージの issue 参照から探す。**本文をここで1回取得してテキストとして保持する**（毎周取り直さない。認証の要る取得をサブエージェントにさせない）

ここで決めたものを最後まで変えない。周ごとに対象がずれると、何が減ったのか分からなくなる。

**完了条件**: 対象ファイル一覧・除外・仕様テキストが確定している。

### 2. 入口ゲートを通す

静的チェックを実行する。赤なら直してから進む。

**完了条件**: ゲートが緑。

### 3. 周を回す

各周で次を行う。

1. **`review-code` を呼ぶ。** 渡すのは凍結したスコープ、仕様テキスト、台帳、そして2周目以降は追加観点（下記）。**実装の経緯や、なぜそう書いたかの説明は渡さない。**
2. **返ってきた指摘を直す。** 直すのはこのスキル自身が行う。レビュアーは判定だけを行い、コードには触れていない。
3. **台帳を更新する。** 下記の形式で、この周の判断を積む。
4. **入口ゲートを再実行する。** 修正で赤くしていないか確かめる。

**2周目以降は追加観点として「直前の周で修正した箇所」を渡す。** 実績上、後の周で出る当たりはそこに集中する。全レンズを毎周フルで回すより、修正差分に寄せた方が同じものを安く拾える。

**完了条件**: 台帳が更新され、ゲートが緑。

### 4. 停止を判定する

次のどちらかで止める。

- **その周の新規指摘（スコア80以上）が0件** — 台帳にある既知のものは新規に数えない
- **4周を終えた**

指摘を0件にすることは目指さない。80未満は最初から捨てているし、80以上でも見送る判断はあり得る。**枯れたかどうかだけを見る。**

4周で止めた場合、まだ枯れていない。そのことを報告に書く。

### 5. 報告する

- 周ごとの、指摘件数・直した件数・見送った件数
- 直した内容の一覧（何が起きるはずだったか、どう直したか）
- **見送った指摘と、その理由**
- 止まった理由（枯れた / 上限）
- 最終のゲート状態

## 台帳

周をまたいで持ち回る。これが無いと、前の周で見送った指摘が毎周戻ってきて、新規かどうかの判定ができなくなる。

各項目に:

- 指摘の要約（同じものだと分かる粒度で）
- `file:line`
- 判断（**適用** / **見送り**）と、その理由
- 何周目のものか

次の周の `review-code` にはこの台帳を渡す。**適用したものも渡す。** 理由なく元に戻す指摘が来るのを防ぐ。
