# guide-pr

大きいPRの本文の先頭に、どのコミットをどう読めばよいかのガイドを置く。数百ファイルのPRを Files changed で開くと、機械的な書き換えの中に手で直した行が埋もれる。レビュアーが読む場所を選べるように、作者がコミット単位で仕分けて渡す。

[annotate-pr](../annotate-pr/SKILL.md) とは役割が違う。annotate-pr は行に「なぜ」を置く。このスキルは、どこを読むかを本文の先頭で示す。両方流すなら、こちらを先にする。

## 入力

PRのURLか番号。無ければカレントブランチのPR（`gh pr view`）を対象にする。

## 手順

### 1. レビュアーに見えるコミットを集める

```bash
gh pr view <PR> --json number,url,baseRefName,headRefName,body,commits,changedFiles
git fetch origin
git log --no-merges --reverse --format='%h %s' origin/<base>..origin/<head>
git show --stat --format='' <sha> | tail -1   # コミットごとの規模
```

Commits タブには、レビュー対象でないコミットも出る。次のものは「飛ばす」に分ける。

- 下に積んでいたPRが squash でマージされたあとも残っている、そのPRの元のコミット。積んだPRなら、下のPRのブランチ（消えていればローカルのブランチ）に含まれるコミットを `git log origin/<base>..<下のブランチ>` で出して除く
- 後のコミットで打ち消した試行。差し引きで何が残ったかは、打ち消した側のコミットに書く

**完了条件**: レビュー対象のコミットが一覧になっていて、それぞれのファイル数と行数が分かる。

### 2. コミットを仕分ける

各コミットを `git show` で読み、次のどれかに分ける。

- **流し読みでよい**: codemod、生成物の再生成、リネーム、同じ置き換えの繰り返し、lockfile。「機械的」と書く前に、差分の行がほぼ同じ形だと確かめる。たとえば `git show <sha> -U0 | grep '^[+-]'` で、置き換えの種類ごとに数える
- **じっくり読む**: 手で書いたロジック、振る舞いが変わるもの、テストの期待値を変えたもの、merge コミットでコンフリクトを解いたところ
- **飛ばす**: 手順1で除いたもの

流し読みのコミットに、じっくり読むべきファイルが混じっていることがある。たとえば、置き換え先のヘルパーを定義したファイル。そのファイル名を、そのコミットの項目に太字で書く。

**完了条件**: 全コミットがどれかに入っていて、「流し読みでよい」には、そう言える根拠（置き換えの種類と数）がある。

### 3. ガイドを書く

PR本文の言語で書く（チームのPRが英語なら英語）。置くのは本文の一番上で、スタック図より前にする。開いて最初に目に入る位置でないと、Files changed に先に行かれてしまう。

````markdown
> [!IMPORTANT]
> **Reviewer guide: about 1,450 files, but most of them are mechanical.** Review commit by commit, not in "Files changed". <飛ばすコミットがあれば、その理由を1文で>
>
> **Skim (mechanical)**
> - [<sha>](https://github.com/<owner>/<repo>/pull/<N>/commits/<sha>) (<n> files): <何の置き換えか>. **Read `<file>` closely**: <なぜ>.
>
> **Read closely**
> - [<sha>](<link>): <何をしたか、どこを見てほしいか>
````

- 1行目は、全体の規模と、大半が機械的だという主張。数は `changedFiles` と手順1の数で書く。「N本だけ読めばよい」のような数は、数えたときだけ書く
- 各項目は、コミットへのリンク、規模、何をしたか。じっくり読む項目には、何を見てほしいかを添える
- テストの期待値を変えたコミットは、何が変わったかと、それが受け入れた違いのどれに当たるかを書く
- 本文の別の場所に古いガイドがあれば消し、先頭の1つだけにする

**完了条件**: 全コミットがガイドのどこかに載っているか、「飛ばす」の説明でまとめて扱われている。

### 4. 本文を更新する

書き込む直前に `gh pr view <PR> --json body --jq .body` で本文を取り直し、その先頭にガイドを足して `gh pr edit <PR> --body-file <file>` で書き込む。ガイド以外の節は取り直したまま残す。レビュアーや他のセッションが本文を書き換えている場合があるから。

**完了条件**: `gh pr view <PR> --json body` の先頭がガイドになっている。

## あとから push したとき

レビュー対応、main の取り込み、上に積んだPRからの merge などでコミットが増えたら、このスキルを流し直す。新しいコミットを仕分けて足し、SHA が変わっていればリンクを直す。古いガイドが指すコミットは、レビュアーの読む順番を狂わせる。

## 報告

会話には次を返す。

- 更新したPRのURL
- 仕分けの要約（流し読み・じっくり・飛ばすが、それぞれ何本か）
- 仕分けに迷ったコミット（どちらとも言えなかった理由）
